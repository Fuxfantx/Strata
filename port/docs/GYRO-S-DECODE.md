# Gyro-S decode: 还能从哪儿拿性能

本文件只谈 **Gyro-S（54.5 GiB / trellis MoE / qwen4exp）的 decode**，每条都给出机制、依据、预期、风险与**验证方式**。
已排除的方向见文末，不要重复。

## 0. 现状账本（本机实测）

| 项 | 数值 | 依据 |
| --- | --- | --- |
| decode | **9.6-9.7 tok/s**（103 ms/token） | `--tokens 9707 --n 32` |
| 每 token 权重字节 | **≈3.33 GiB**（Q5_K 1.82 + K 输出 0.50 + Q8_0 0.39 + 专家 0.47 + 其它） | `port/tools/weight-report.py` 按 header 偏移 |
| GPU 时间 | **≈40 ms**（≈80 GB/s） | `GGML_VK_SERIALIZE_SUBMISSIONS=1` 对照 |
| 进程 CPU | **≈25 ms** | 引擎 `cpu` 计数 |
| **未解释** | **≈38 ms** | 103 − 40 − 25（**假设，需验证**，见 §1） |
| 本机可读带宽 | 137-145 GB/s | `port/tools/membw.cpp` |

### 0.1 一组需要更正的数字

阶段文档里曾写 `q5_K 46 GB/s`、`q6_K 59 GB/s`（来自早期冷缓存测量）。本机重测（`mm-probe`，warm，400 次）：

| 类型 | int8（q8_1）路径 | f32 路径 |
| --- | --- | --- |
| `q5_K` | **71.1 / 72.5 GB/s** | 67.5 / 69.5 GB/s |
| `q6_K` | 87.5 / 76.9 GB/s | **86.6 / 85.6 GB/s** |

⇒ Gyro-S 的 dense 类型本身并不慢（≈72-87 GB/s）；**它占 55% 的字节量，是"量"的问题，不是"率"的问题**。

### 0.2 一个此前没注意的事实：整包是 **mapped**，不是读进来的

```
--load-mode: the pack (54.5 GiB) does not fit in RAM available now (39.2 GiB), so it is mapped rather than read
```

于是 `per_layer_token_embd.weight`（**IQ4_NL 26.8 GiB**）的每一行都是 **mmap 页**。而每 token 要 gather **48 行**（每层一行，
约 1.4 KB/行，共 ≈67 KB），这 48 个地址分布在 26.8 GiB 的随机位置 ⇒ **每 token 可能是 48 次 NVMe 读**。
页错误**不计入进程 CPU 时间**，这正好解释了 §0 里那 38 ms 的缺口（假设）。

overlay 里**已经有** `src/llama-ple-disk.cpp`（直接 I/O + 256 MiB 直接映射行缓存 + `gather()`），
但本机这次加载**没有启用**（引擎日志没有 on-disk PLE 那一行，`disk_bytes = 0`）。
而且在当前分支上它**没有任何调用点**（`grep llama_ple_disk` 只出现在它自己那两个文件里）——这份实现是**死代码**，所以 A1 的“启用”实际等于“把它接回加载器并加一个引擎开关”，不是调参。

## 1. 手段 A：把 PLE 的 48 次随机读变成 1 次（**最高优先**）

| 步骤 | 做法 | 预期 | 风险 |
| --- | --- | --- | --- |
| A0 | **先证明**：临时把 gather 索引强制成 0（所有层读同一行，输出变垃圾但量化值仍合法、不会有 NaN）→ 若 decode 明显变快，缺口确实是 PLE | 只回答"A 值不值得做" | 极低（试验开关，随后移除） |
| A1 | **启用已有的 `llama_ple_disk`**，并把 `cache_bytes` 从 256 MiB 提到 512-1024 MiB、**直接映射改 4 路组相联**（26.8 GiB 表 / 256 MiB 缓存 = 0.9% 容量，直接映射冲突严重） | 命中率提高，页错误减少 | 低（代码已存在） |
| A2 | **热行侧表**：把真正用过的行复制进常驻缓冲（LRU）。自然语言 token 分布偏斜，"the"/" of" 这类高频 token 的行会反复命中 | 未命中率显著下降 | 低-中 |
| A3 | **批量 + 排序**：一个 token 的 48 个偏移在采样后**立刻全部知道**，用一次批量 positional read（或 `readv`）代替 48 次独立读，且按偏移排序让 NVMe 顺序化 | 队列深度利用率提高 | 低 |
| A4 | **换位布局**（一次性代价大）：把 `[layer][token]` 改成 `[token][layer]`，一个 token 的 48 行连续 → **1 次 67 KB 读**取代 48 次随机读 | 最彻底 | 高：需要额外 26.8 GiB 磁盘与一次全表重写；成品 pack 需要重新打包 |

**判据**：A0 若显示缺口 <5 ms，则 A1-A4 都不值得做；若 ≥20 ms，A1+A3 应能拿回一半以上（**+15-30% decode**）。

## 2. 手段 B：dense 层的字节量（1.82 GiB Q5_K = 55% 流量）

字节量是 Gyro-S 的真瓶颈（42 ms 里有 ~23 ms 是 Q5_K 那 1.82 GiB），但**无损手段极少**：

| 选项 | 字节变化 | 画质 | 可行性 |
| --- | --- | --- | --- |
| 保持 Q5_K（现状） | — | — | — |
| **Q5_K → Q4_K**（4.5 bpw） | −18% | 轻微下降 | 需重量化 dense 层 + 困惑度代理 |
| **Q5_K → trellis TQK6**（2.125 bpw，87 GB/s） | **−62%** | 明显下降 | 需重量化；但 Gyro-S 的专家已是这个比特率 |
| **输出层 Q6_K 497 MiB → Q5_K** | −18%（该张量） | 轻微 | 需重量化 |

> 这一组**违反"不降精度"**，因此只能在明确接受画质代价时采用；建议先用 100 句文本的困惑度对比做**代价-收益**表。

## 3. 手段 C：限制 logits 词表（有损但机制已在仓库）

`output.weight` 是 Q6_K **497 MiB = 流量的 15%**。仓库里已有 `--draft-vocab data/draft_vocab_*.bin` 与 `data/draft_vocab*` 这套机制
（原本给草稿词表用）。把 logits 限制在 32k 词表：**−70~80% 的 output 读取 ⇒ +8-10% decode**。
代价：词表外的 token 不可达。**只有在用户作品明确不需要**冷僻 token 时才可考虑。

## 4. 手段 D：把 25 ms 的 host 侧压下去（无损）

| 选项 | 做法 | 先测什么 |
| --- | --- | --- |
| D1 | `--threads 4/8` 与 `--perf-cap` 的 A/B | 25 ms CPU 里有多少是线程争用 |
| D2 | 图缓存（拓扑不变、只换指针） | 之前分桶只解释了 5.6 ms，其余在驱动线程；先确认可动范围 |

## 5. 手段 E：dense 层走 int8 matvec（数值会变）

实测 `q5_K` int8 比 f32 **+3%**、`q6_K` 两者相当（噪声内），并且会把激活量化到 int8 ⇒ **可能改变 token 流**。
只有在允许数值变化、且 32-token 门禁仍相等时才采用；否则按纪律放弃。

## 6. 不建议再试（本阶段已实测排除）

| 方向 | 结论 |
| --- | --- |
| 减少 dispatch 条数 | 每次 0.49 µs；1/4/26 次提交吞吐相同 |
| `FORCE_MMVQ`（Qualcomm 走 matvec） | 五对 ABBA 只有 2/5 赢 |
| Q2_0 的 128 B 重排 | 非带宽受限 |
| 跳过转换/算子来定价 | 污染下游数值，方法失效 |
| MTP / 投机 | 本 pack **没有 nextn 张量**，不可评估 |
| `fwht` 融合 | 96 次 dispatch 的成本低于噪声 |

## 7. 建议顺序

1. **A0**（15 行试验，2 次运行）：给那 38 ms 定性 —— 这一步决定 A 组值不值得做；
2. 若成立：**A2 + A3**（热行侧表 + 批量读），再考虑 **A1**；
3. 同时可做的无损项：**D1**（线程/核数 A/B，1 次）；
4. 只有在画质可接受时，才进入 **B/C** 的字节量削减，并先做困惑度对比表。

**每项判据不变**：零对照测当轮噪声底、ABBA 交替、以成对中位数为准；≥0.2% 才立项，<0.2% 如实记录并回滚。
