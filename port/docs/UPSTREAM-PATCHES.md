# Patches worth offering upstream

Everything here already lives in this tree - `port/llama-overlay-vanilla/` for the llama.cpp side, `port/engine/` for the
engine. This note is the shortlist that is **not** fork-specific: each entry says what it changes, why the measurement
justifies it, and where it is. Numbers are from `ADRENO.md` on this machine.

## Where the repin stands

The tree is on upstream `b12722` (commit `e6443bd7e`), regenerated by `fetch-llama.ps1` from the vanilla source plus
`port/llama-overlay-vanilla`. What is verified today, with the command that verifies it:

| Area | State | Evidence |
| --- | --- | --- |
| Text generation, default cache | matches the CPU backend token for token | `strata-vk --tokens 9707 --n 3 --max-context 1024 --kv f16` gives `25,3437,369`, the CPU's own output |
| `CPY` into a quantised type | fixed (block count vs element count in the generator's source sets) | `cpy-probe` reports 0 differing bytes; `test-backend-ops -o CPY` 271/271 |
| `SET_ROWS` | fixed (the pipelines now declare the parameter block they read) | `test-backend-ops -o SET_ROWS` 279/279 |
| Quantised KV cache | q4_0 works and matches the CPU tokens; q8_0 still stays f16 | `--kv q4_0 --n 3` gives `25,3437,369`, the same as f16 and the CPU; `GET_ROWS -p type=q4_0` is 11/11 |
| `MUL_MAT` | 2435/2684 | `test-backend-ops -o MUL_MAT`, was 2427 before the copy fix |

Open items are listed at the end of this file: a quantised K/V flash-attention path for Vulkan (the real fix behind the
refusal above), the `q1_0`/`nvfp4` generic matmul path, and the shader-conventions migration of the remaining
push-constant sources.

## Backend (llama.cpp, `ggml/src/ggml-vulkan`)

1. **Cooperative-matrix capability detection without an f32-accumulate assumption.**
   `ggml_vk_instance_init` disables every matrix-core path when the device has no f32-accumulate f16 matrix
   (`f32acc 0`), even when it does report an f16-accumulate one. Qualcomm's Adreno X2-90 is exactly that device. The change
   lets a device with `coopmat_acc_f16_support && !coopmat_acc_f32_support` build the `*_f16acc` pipelines, accounts the
   staging at 2 bytes per element in the shared-memory check (26624 of 32768 bytes for the 64x64 tile), and lets
   `ggml_vk_get_mul_mat_mat_f16acc` return true there. Measured: 27B pp512 77.5 -> 163.9 tok/s, 35B-A3B 148.6 -> 198.9 (and
   598 with flash attention), with identical CPU-vs-Vulkan token streams.

   > **Withdrawn (2026-11-18).** "Identical token streams" was a 32-token comparison and it is false: the kernel's logits
   > correlate 0.02 with the CPU backend's and the top token changes (`PERFORMANCE-LOG.md` §4.1). The engine no longer enables
   > it by default. The capability-detection patch itself is still right - it is what makes the f32-accumulate cooperative
   > matrix reachable, which is the default path today.

2. **Pipeline-map lookup falls back to the `f16acc` key.** With the capability above, a plain request finds nothing because
   only `*_f16acc` variants exist; the lookup retries with `f16acc = true` and warns nothing. (`GGML_ASSERT(mmp_map !=
   nullptr)` is what it replaces.)

3. **`prefer_f16_b` should be a shape rule, not a vendor list.** Upstream prefers an f16 B for Intel only. Two additions are
   needed for correctness and speed elsewhere:
   * prefer it only when a real token batch is present (`ne[1] || ne[2] || ne[3] > 1`), because an f16 B disqualifies the
     matvec kernel and decode regresses (tiny 130.7 -> 112.3 tok/s when that was missing);
   * require tile-legal dimensions (`k % 128 == 0`, `m % 64 == 0`, `n >= 64` for the dense path; plus `n_mats >= 16` and
     `k >= 256` for the grouped path), because the cooperative shader has no tail handling. This is the whole accuracy
     remedy: the oracle goes from 20/38 (garbage on partial tiles) to 38/38 in both precision modes with zero cost on the
     model shapes.

4. **Create the cooperative pipelines in both shader arms.** The block that creates them sat inside the fp32 arm; the packs
   that run in fp16 mode (every mixture-of-experts pack here) never reached it, so their grouped matmuls logged
   `prefer_f16_b=1 f16_avail=0` and stayed on the dp4a path. A self-contained creation block in the fp16 arm (dense and
   grouped) is worth 35B-A3B prefill 195 -> 502 tok/s and Gyro-M 34 -> 197.

5. **Open defect worth reporting: direct backend graphs return zeros for the cooperative kernel.** `mm-probe` and
   `test-backend-ops` submit a single-node graph straight to the backend and get an all-zero result for every shape, while
   llama.cpp's scheduler path computes the same shapes correctly. It is why the oracle could not certify this kernel before
   the shape gate; a fix in the prealloc/reformat planning of the direct path is the missing piece.

## Engine (this port, `port/engine`)

6. **Per-model shader route from the GGUF header** (`vk-devices.cpp`, `ModelFacts`): dense models want the fp32 shaders,
   packs whose int-dot tensors are all 2-bit want the fp16 shaders with `GGML_VK_DISABLE_INTEGER_DOT_PRODUCT=1` (their dp4a
   fp16 shader crashes this driver on a multi-token prefill), trellis packs want the fp16 shaders for decode. This is worth
   2-3x on the low-bit packs and costs nothing.

7. **Flash attention chosen from the context length and the model size** (`vk-engine-load.cpp`): off below 8k context and for
   small models (a 24-layer model loses 38% decode with it), on above 8k for models with 32+ layers, where it is worth 81% on
   a 4k prefill (f16 KV) and 31% with q4_0 KV. `--flash-attn` always wins.

8. **`--perf-cap` is opt-in only** (`vk-common.h`, `vk-options.*`): it sleeps the owed idle share per step and pins the
   process away from the reserved cores. It exists because a benchmark otherwise consumes the whole machine, but note for
   anyone reusing it: it cannot cure stutter caused by paging (see `ADRENO.md`), and millisecond-accurate sleeps need the
   spin-loop that is there because Windows' timer granularity is ~15.6 ms.

9. **A pack larger than RAM is mapped, not read** (`vk-engine-load.cpp`): `--load-mode direct` reads every byte of the file   into a buffer, including the N-Gram/PLE table that mmap can leave in the file, so on an oversized pack it is exactly
   what fills the RAM. When the user did not name `--load-mode` and the pack is bigger than `ullAvailPhys`, the engine now
   maps it. Measured on Gyro-S (54.47 GiB pack, 15.27 GiB of it that table, 40.3 GiB free): 4.1 -> 6.1-6.4 tok/s decode,
   with 0.6 GiB still free at the end of the load and the disk idle during decode. Small packs keep the direct path, which
   loads them 1.5-1.7x faster (`ADRENO.md`).

10. **Host experts turn the f16-accumulate cooperative matrix off** (`vk-devices.cpp`, `vk-engine-load.cpp`): the policy   above opts into `STRATA_VK_F16ACC` for prefill speed, and with experts on the CPU that combination miscomputes as soon
   as a batch carries more than a handful of tokens - Gyro-S and Gyro-M abort in `ggml-cpu`'s swiglu NaN check at 12
   tokens (8 is fine), while the same model on device experts is clean at 6, 12 and 32 and vanilla `llama-completion
   --cpu-moe` finishes the same prompt because it never enables f16acc. `f16acc_from_policy` records that the engine (not
   the user) turned it on, and the host-expert branch sets it back to 0 with a log line. Measured: `--bench-pp 64
   --cpu-moe` went from an abort to 6.82 tok/s on Gyro-S and 7.94 on Gyro-M, with the device-expert path unchanged
   (90.9 tok/s at pp64).

11. **One single-token forward at the end of the load** (`vk-engine-load.cpp`, `STRATA_VK_NO_WARMUP` disables it): a
   mapped pack is page-cold and the first graph pays for it - the same `MUL_MAT_VEC q8_0 m=10240 n=1 k=320` measured
   96 x 4985 us on the first graph and 96 x 2.5 us on the next one, which is 11 MB at 23 MB/s against cache speed, and
   made the first decode step 3.35 s against a 99.8 ms steady state. The forward costs 5.25 s once, inside the load, and
   moves the user-visible `prompt` from ~5100 ms to **111 ms** (decode n=8 went from 6.5 to 11.0 tok/s purely from not
   averaging that stall in). A multi-token warmup would also warm the cooperative pipelines, but leaves a hybrid model's
   memory in a state the next decode rejects (M-RoPE asserts on position order even after `llama_memory_clear`), so only
   the single-token one is here; item 12 warms the prefill pipelines the safe way.

12. **A throwaway 16-token context warms the prefill pipelines** (`vk-engine-load.cpp`, same `STRATA_VK_NO_WARMUP`): the
   prefill graph takes different pipelines from a decode step and the first six-token prompt spent 2.4 s compiling them.
   Doing the multi-token forward in the real context corrupts a hybrid model's memory, so the load creates a second
   context with `n_ctx`/`n_batch` of 16 and no MoE cache, decodes 16 tokens, and frees it - the pipeline cache belongs to
   the device, the context only supplies a graph. Measured: the first real prompt went from 2423 ms to **780 ms** for
   2.87 s of extra load time, with the reference tokens, Paris and pp64 (92.95) unchanged.

13. **An oversized pack keeps its experts on the device when they fit** (`vk-engine-load.cpp`): the host-expert staging
   is for packs whose *experts* are bigger than RAM, but it used to trigger whenever the whole resident set was. For Q2_0
   (62.2 GiB pack, 31.6 GiB of experts, 40 GiB free) that was the wrong side of the line: one token touches only ~0.6 GiB
   of experts and the page cache keeps that set, while the staging pays a 4 GiB device bank against 31.6 GiB of host
   experts and spends 56% of the wall in the loader. Leaving them on the device measured **3.3 -> 14.2 tok/s decode and
   17.1 -> 40.4 tok/s at pp64**; a larger bank is worse, not better (8 GiB: 2.9 tok/s and 767% CPU, because the bank and
   the page cache evict each other). Gyro-M gains the same way (pp64 65.3 -> **95.5**), Gyro-S is untouched because its
   resident set fits, and `--cpu-moe` still forces the old placement.

14. **Four shaders that the backend depends on are now tracked in the overlay** (`ggml/src/ggml-vulkan/vulkan-shaders/`):
   `dsv4_hc_pre.comp`, `dsv4_hc_post.comp`, `dsv4_hc_comb.comp` and `lightning_indexer.comp` existed only under
   `third_party/llama.cpp`, so the next re-fetch of upstream would have dropped them and silently changed every qwen4exp
   forward pass - the C++ side (`ggml-vulkan.cpp`) was in the overlay but its shaders were not. Copying them brings the
   overlay to 58 files with zero mismatches against `third_party`; the build is byte-identical in behaviour (the
   reference 32-token stream is unchanged).

15. **`GGML_OP_GATED_MUL`: one op for `x * sigmoid(gate)`** (`ggml.h`, `ggml.c`, `ggml-cpu/ops.{cpp,h}`,
   `ggml-cpu/ggml-cpu.c`, `ggml-vulkan/ggml-vulkan.cpp`, `ggml-vulkan-push-constants.h`,
   `ggml-vulkan-types.h`, `vulkan-shaders/gated_mul.comp`, `vulkan-shaders-gen.cpp`, `src/models/qwen4exp.cpp`).
   The three gate sites in qwen4exp emitted `sigmoid` followed by `mul`; the backend's `SIGMOID_MUL` fusion requires the
   two nodes to be adjacent, and this fork's graph builder interleaves sibling consumers between them, so the pair cost
   two dispatches each. The op takes `x` and the *raw* gate and applies the sigmoid internally, in the same broadcast
   form as `ggml_mul`'s second operand (one value per row when `gate->ne[0] == 1`). Op count 99 -> 100, hence the two
   `static_assert`s in `ggml.c`. Measured on Gyro-S decode: 2728 -> 2668 dispatches per token and 9.60 -> 9.70 tok/s
   (median of three runs), reference 32-token stream identical.

16. **The node range edge dump** (`ggml-vulkan.cpp`, since removed): it printed each node's real sources inside a node
   range, which is how the non-adjacency above was diagnosed. No behaviour change then or now.

## Trellis types: TQ2_T / TQK6 / TQK7

**Provenance.** The Vulkan shaders, the reference codecs and the CPU dot kernel are transplanted from
`https://github.com/agentionai/llama.cpp` (MIT licence), branch `main` at `dc255f2a`, with the Vulkan matvec tuning of
`perf/strix-vulkan` at `3c75be02` (the word-view state extraction in `tqk.glsl`). One tuning value diverges from the fork:
`rm_tq` (rows per workgroup in the matvec) is `20 * rm_stdq`, not 1, reachable through `STRATA_VK_TQ_RM_MULT`. The range
was swept on Gyro-S decode at n=16: 2x gives 6.1 tok/s, 4x 7.8, 8x 9.1, 12x 9.8, 16x 9.9, **20x 10.4**, 24x 10.1, 32x 9.5,
so the workgroups were far too fine-grained (a 4.5x change in rows per workgroup bought 70%). A workgroup unpacks a whole
6-bit row from the stream, so fewer, fatter ones amortise the unpack setup. Prefill is unchanged (pp64 88.8, pp512 217.4)
and the TQK oracles stay green (MUL_MAT 37/37, MUL_MAT_ID 75/75). The earlier 2x figure came from sweeping only {1,2},
which was the mistake this corrects. The tree
already carried **TQ2_T (id 144)** from ggml-org upstream (`32bdc3a8`): block layout, the 4x2048 fp16 codebook,
`quantize_row_tq2_t_ref`/`dequantize_row_tq2_t`, `ggml_vec_dot_tq2_t_q8_0`, `dequant_tq2_t.comp`, the
`mul_mat_vec`/`mul_mat_vec_id` TQ2_T branch and the `types.glsl`/`dequant_funcs.glsl` hooks. Only the two bit-packed siblings were
missing, so the transplant is the **TQK6/TQK7 delta** of the same format:

* `ggml-common.h`: `QK_TQK`, `block_tqk6`/`block_tqk7`, `tqk_state()` and its bit helpers, static asserts.
* `ggml-quants.c`: `tqk_set_chunk`, `quantize_row_tqk*_ref`, `dequantize_row_tqk*`, `quantize_tqk6/7` (identical value formula to
  TQ2_T, the state window is the only difference).
* `ggml-cpu/quants.c`: the `ggml_tq_state_i16` table, its `GGML_TQ_I16_SCALE = 2^13` fixed point and
  `ggml_vec_dot_tqk{6,7}_q8_0`, plus the one-time `ggml_cpu_tq_init()` call. Scalar only: the x86 SIMD variants are of no use on
  ARM64.
* Vulkan: `tqk.glsl` (byte and word views of the circular 16-bit window), `dequant_tqk6/7.comp`, the `accumulate_tqk` branch of
  `mul_mat_vec.comp` (four 16-bit loads per lane per row), the `mul_mm_funcs.glsl` staging branch for the mat-mat path, the
  `dequant_funcs.glsl` `tqk_state`/`dequantize` hooks, and the generator + pipeline wiring in `ggml-vulkan.cpp`.

**Verification.** `test-backend-ops -o MUL_MAT -p type_a=tqk{6,7}` 37/37 and `-o MUL_MAT_ID` 75/75 for both types, against the
CPU reference (which the oracle reaches through the same `vec_dot`, so the independent check is the token comparison below). The
pack `Gyro-S-TQ1_0.gguf` loads and generates, and the same eight tokens come out of three placements of the same weights: host
experts (CPU `ggml_vec_dot_tqk*`), device experts with a 24 GiB cache, and device experts with mmap paging - the default
placement now maps the pack (see engine item 9) and decodes at 6.1-6.5 tok/s, against 4.1-4.2 with the whole pack in
buffers. The Hadamard hint needs no work: `ggml_vk_can_use_fwht` already honours `GGML_HINT_SRC0_IS_HADAMARD` and
the tree carries the fused FWHT pipeline for the 136 rotated expert tensors.

**Defects found on the way, both reproducible without the trellis types (Gyro-M):** the host-expert MoE cache reads its device bank
past the rows it allocated for a multi-token prefill (`ffn_moe_gate-1 bad=1542/409600`), and `GGML_OP_LIGHTNING_INDEXER` returns
all-NaN for some placements. `GGML_NAN_SCAN=1` (CPU) and `GGML_VK_NAN_SCAN=<substr|*>` (Vulkan) are the two scans that localise
them; both are env-gated and cost nothing when unset. `GGML_VK_GRAPH_PRINT=1` is the third knob: it dumps the shape and name of
every elementwise node in each graph, which is what `GGML_VK_PERF_LOGGER` cannot show, because a fused dispatch (the eight
`[2560,1]` adds of `ffn_moe_out` become one `MULTI_ADD`) is logged under the fused name only.

**Correction on the indexer (round 16):** the `LIGHTNING_INDEXER` "NaN" was `-inf`. Those scores are masked-out pools, which is
the intended value, and the scan was counting every non-finite value as a NaN. The scan now reports `nan= / -inf= / +inf=` and
the index of the first bad element, and `GGML_VK_NAN_SCAN_PIN=<substr>` pins the matching nodes as graph outputs first, so a
post-graph scan reads their own bytes instead of a buffer the allocator already recycled.

Two real defects the same round did find, both outside the kernels: the unfused indexer-mask fallback in `qwen4exp.cpp`
(`set_rows` + `cumsum` + dump rows) miscomputes when a ubatch carries more than one token, and it is the path every backend
takes when `LLM_FUSED_OP_TOP_K_MASK` does not resolve (the CPU one among them); and every fused-op probe in `llama-context.cpp`
is built with `n_tokens_per_seq = 1`, so the fused paths were never validated on a multi-token prefill. `STRATA_NO_FUSED_LID=1`
and `STRATA_NO_FUSED_TOPK_MASK=1` isolate the two indexer fusions the way `STRATA_NO_FUSED_HC=1` isolates the hc one.

## Backend fix worth offering upstream: the shader generator deadlocks on Windows

`execute_command()` in `vulkan-shaders-gen.cpp` drains `stdout` to EOF and only then reads `stderr`. A `glslc` child that fills the
64 KiB stderr pipe before closing stdout blocks forever, and so does the parent: a build wedges with every compiler process idle at
~0.1 s of CPU and no progress (seen here with 12 `glslc` processes, no disk activity, 2 minutes of wall time). Routing both streams
into one pipe and reading that single stream removes the deadlock; keep the diagnostics by copying the captured text into
`stderr_str`.

17. **`STRATA_VK_TIME=1`: where a decode step's wall time goes** (`ggml/src/ggml-vulkan/ggml-vulkan.cpp`,
   `ggml/src/ggml-vulkan/ggml-vulkan-common.h`).  A stopwatch over a graph's recording, six buckets inside it (the
   dispatch helper, `ggml_vk_sync_buffers`, the fusion chain, `ggml_vk_ctx_end`, `ggml_vk_submit` and the command pool
   cleanup), the fence wait in `ggml_backend_vk_synchronize`, and one line per token.  Off by default with no overhead.

   It first looked as if a decode step were CPU recording-bound (Gyro-S recording 100.7 ms and waiting 0.001 ms for a
   91 ms token), and the buckets show that reading was wrong: the dispatch helper costs 0.49 us per call, a barrier
   0.04 us, the whole fusion chain 0.16 us per node, and cleanup 0.12 ms, which is about 3 ms of host work in a 72 ms
   window.  Splitting the graph into fewer command buffers was measured through an experimental cap on submissions
   and confirmed it: 1, 4 and 26 submissions all gave the same throughput. That cap, and the per-pipeline counters
   added beside it, have since been removed from the tree; the measurement is what remains.  With `GGML_VK_SERIALIZE_SUBMISSIONS=1` a Q2_0 token falls from 15.5 to
   9.5 tok/s, which exposes about 40 ms of GPU work against roughly 25 ms of process CPU, so a token is 40 ms of GPU
   plus 25 ms of CPU, partially overlapped.  `port/docs/PERFORMANCE-LOG.md` records the correction; the knobs
   stay because proving what is not the bottleneck is worth an environment variable.

18. **The dp4a mat-mat shader is taken from the fp32 module** (`ggml-vulkan.cpp`, `ggml_vk_load_shaders`).
    Both modules are compiled into one binary and the creation order decides which one a pipeline slot gets
    (`create_mm_pipelines` returns early when the slot is already `initialized && compiled`), so the fp16-module
    `matmul_*_q8_1` lines silently beat the fp32-module ones that follow them. Pointing the three fp16-arm
    `sg_create_mmq` runs at the `*_fp32_len`/`*_fp32_data` symbols - types, pipeline keys and tile configs
    unchanged - moves only the int-dot **mat-mat** to fp32 while the mat-vec and every elementwise shader stay on
    the fp16 module. Measured on Gyro-S on 2026-11-18 (interleaved 3 rounds, `ggml-vulkan.dll` swap, medians):
    **pp512 16.01 -> 49.80 tok/s (+211%)**, tg16 10.17 -> 10.12 (noise), bench prompt 5 840 -> 3 050 ms;
    these are same-day comparisons, not the current default - what the default does today is in
    [`PERFORMANCE.md`](PERFORMANCE.md);
    `test-backend-ops -o MUL_MAT -b Vulkan0` 3/3 and `OK`; the two modules agree on logits at correlation
    0.999424 with the same argmax. The reason the fp32 module is faster is the one `--shader-family fp32` already
    showed (ADRENO.md: "the fp16 shader variants cost the int-dot matmul a factor of four"), now obtained without
    paying that switch's decode cost.

## 搬家到新钉点（b12722）的做法

`port/llama-overlay-vanilla/` 存的是**整份文件**，所以换钉点时不能直接把 overlay 覆盖到新上游上：那会把上游在这些文件里的
改动一并丢掉。第一次尝试 b12722 就因此失败——overlay 的 `ggml/include/ggml.h` 还是旧钉点的版本，而新上游自己的
`ggml/src/ggml-alloc.c` 已经引用了那个头文件里新增的算子。

正确做法是**逐文件三方合并**（工具：`port/tools/repin-merge.py`）：

```
base   = 旧钉点的 vanilla 树
ours   = overlay 里这一份
theirs = 新钉点的 vanilla 树
```

合并干净的文件写回 overlay；有冲突的文件保持原样并列出，由人决定。用 b12722 实测的结果：

| 类别 | 数量 |
| --- | --- |
| 只在 overlay 里新增（上游没有） | 31 |
| 三方合并干净 | 66 |
| 需要人工判断 | 16 |

十六个冲突集中在：`ggml.h`、`ggml.c`、`ggml-cpu.c`、Vulkan 后端的 `ggml-vulkan.cpp` / `-types.h` /
`-push-constants.h` / 四个 shader / 生成器，以及 `llama-context.cpp`、`llama-graph.cpp`、`llama-quant.cpp`、
`delta-net-base.cpp`、`qwen4exp.cpp`。

两个 vanilla 树需要**完整**：先用 `curl.exe`（不要用 `curl` 的别名，也不要用 PowerShell 的 `>` 重定向，它会把二进制
写成 UTF-16）下载，并核对条目数量（旧钉点 4 596 条、新钉点 5 180 条）；不完整的树会让"我们新增的文件"被误判成
"双方都新增"，从而把真正的冲突藏起来。

### b12722 合并后的 Vulkan 数值问题（进行中）

构建通过、商品路径能跑，但 Vulkan 输出与 CPU 不一致（同一 pack、同一 prompt：CPU 首 token 正确，Vulkan 全错，且与
flash-attn、cooperative matrix 无关）。用仓库自带的后端测试套件可以把它限定到算子：

```
cmake -S third_party/llama.cpp -B build -DLLAMA_BUILD_TESTS=ON
cmake --build build --target test-backend-ops
build/bin/test-backend-ops.exe -b Vulkan0 -o MUL_MAT      # 2065/2684 通过
```

失败集中在**非量化 A（f16 / f32）× f32** 的 `MUL_MAT` 家族（量化 A 的用例通过），因此问题在通用 matmul
（`mul_mm.comp` + `mul_mm_funcs.glsl`）这一侧，而不是 `mul_mmq`。

一个关键的合并限制：**不能整份替换 `mul_mm.comp`**。实测把上游 b12722 的版本换进来有两处后果——一是编译失败
（`mul_mm_funcs.glsl` 调用 `ptq1_0_trits8`，而该 helper 的 `#include "ptq1_0.glsl"` 原来写在我们的 `mul_mm.comp` 里。
已改为由 `mul_mm_funcs.glsl` 自己包含，这是更正确的依赖方向）；二是即使编译通过，后端在设备初始化阶段就退出，说明
上游那份 .comp 的接口（参数块与 dispatch 约定）与我们合并后的 C++ 不同。结论：这两个文件必须**逐块合并**，不能替换，
并以 `test-backend-ops` 作为逐步验证的门禁。

### 参数块（binding 12）的落点：合并后丢失的线索

本端口把部分 shader 的标量放进**参数块**（`PARAM_BLOCK_ENABLED`，binding 12），生成器里目前有 51 个 shader opt in，
其中包含 `mul_mm.comp` 与 `mul_mmq.comp`；`ggml-vulkan-shader-meta.h` 也把 `matmul` 家族声明为 `param_block = true`。

合并后的 `ggml-vulkan.cpp` 里只看到 `pipeline->uses_param_block` 被**赋值**（meta 与家族名两处），却**没有任何读取点**，
而 `ggml_vk_begin_param_block()` 仍然存在并被调用。也就是说：编译进 `PARAM_BLOCK_ENABLED` 的那 51 个 shader 会去读
binding 12，但派发侧是否真的写入并绑定这个块，无法从当前代码确认。

后续核查推翻了这一猜测：整个后端目录里 `param_block|PARAM_BLOCK` 的匹配数在 pre-repin 与合并后**完全相同（各 40 处）**，
机制没有被合并破坏。真正的差异在 shader 本身——

上游 b12722 的 `mul_mm.comp` 引入了 **stream-K**：tile 的选取改由 `p.k_units_per_tile`、`p.blocks_m_mp`、
`fastdiv_L(p.div_Ls0, ...)` 等新字段计算，而我们那份是没有 stream-K 的旧实现。合并后的 C++ 已经在传这些新字段，
旧 shader 却忽略它们 ⇒ 走到 matmul 路径的用例会**选错 tile**、数值全错，而小尺寸走 `mul_mat_vec_*` 的用例仍然正确。

因此修复方向是**让 shader 采用上游的 stream-K 实现**，并把本端口的类型分支（PTQ1_0 / TQ2_T / TQK6 / TQK7）移植进去，
而不是继续在 C++ 侧找"丢失的消费者"。

### 直接换入上游 stream-K 版 `mul_mm.comp` 的实测结果

换入后**可以编译**，但进程在后端初始化阶段就中止（退出码 `0xC0000409`，与商品路径偶发的那个签名相同），
`test-backend-ops` 连一条用例都跑不到。恢复到我们的版本后基线回到 `2065/2684`。

原因是接口层面的：上游的 `mul_mm.comp` 声明了参数块（binding 12），而这棵树里 `pipeline->uses_param_block`
只被赋值、没有派发侧的使用者，`ggml_vk_create_pipeline` 的 `param_count` 也没有把 binding 12 计入。两者对不上时
管线创建会触发断言而中止。

因此有两条路，且必须选一条走到底：

1. **补齐参数块**：让派发侧真正写入并绑定 binding 12，并把 `param_count` 计入它。这样上游所有 stream-K shader 都能直接使用，
   也符合 `port/docs/SHADER_CONVENTIONS.md` 中"标量走参数块"的约定；
2. **把 stream-K 移植进我们的 shader**：保留推常量接口，只搬 tile 选择那段（差异已存于
   `port/docs/features/mul_mm_vs_upstream.diff`）。

从"形式更优"与约定一致性看，第 1 条更彻底；从风险看，第 2 条改动面小。两者都需要 `test-backend-ops` 的 2684/2684 作为门禁。

### 参数块机制其实是完整的（更正），缺的是 stream-K 的 **C++ 侧**

再核查后要更正前面两处推测：参数块并不是"没有消费者"。`ggml-vulkan-common.h` 的派发模板里已经实现了完整路径——
`pipeline->uses_param_block` 为真时，把推常量写进 `ctx->param_block` 的第 `slot` 个位置、用动态偏移绑定
`PARAM_BLOCK_BINDING`，并且 `device->dsl` 里 `MAX_PARAMETER_COUNT` 那个 binding 就是按 `eStorageBufferDynamic` 建的。
`ggml-vulkan-shader-meta.h` 也把 `matmul` 声明为 `param_block = true`。这一层没有问题。

真正缺的是 **stream-K 的参数由谁算**。实测：把上游的 `mul_mm.comp` 换进来后，引擎在第一次提交时报
`vk::Queue::submit: ErrorInitializationFailed`（测试进程则表现为 `0xC0000409`）。对照 C++ 侧可见原因：

```cpp
// ggml_vk.cpp 里我们这一版的 matmul 推常量，字段止于 padded_n
ggml_vk_matmul(..., split_k, ne12*ne13, ne02, ne12, r2, r3, padded_n, ...);
```

而 `vk_mat_mat_push_constants` 在合并后还包含 `k_units_per_tile`、`blocks_m_mp`、`blocks_n_mp`、`work_units_per_group`、
`groups_with_extra_unit`、`div_Ls0`、`div_Ls1` 等 stream-K 字段——我们这一版**没有计算它们**（保持为 0）。上游 shader 用
`fastdiv(..., p.k_units_mp, fastdiv_L(p.div_Ls0, ...))` 选 tile，除数为 0 自然算出非法索引，最终在提交阶段炸掉。

因此这项工作的主体是**把上游 `ggml_vk_matmul` 的 stream-K 参数计算与派发网格搬过来**，shader 与 C++ 必须成对移植；
单独换 shader（已试）或单独改 shader（路径 2）都不成立，因为网格形状本身由 C++ 决定。

### 参数块无问题；下一步按性能日志的实测形状钉住 tile

`PARAM_BLOCK_SLOTS = 8192`、`PARAM_BLOCK_STRIDE = 256`（`ggml-vulkan-types.h`），每张图开始时
`ggml_vk_begin_param_block` 会把 `param_slot_next` 清零并切换奇偶半区，因此不存在槽位复用错乱的问题；
这一条也可以排除。

剩下的嫌疑集中在 **tile 的常量化参数**（`BM / BN / BK / WM / WN / WMITER` 与 `wg_denoms`）：合并后这些值来自
上游新的选取逻辑，未必与本机实测最优、也未必与 shader 里的 `constant_id` 一致。

按既有实测，本机最优形状记录在 `port/docs/PERFORMANCE-LOG.md`（阶段二重建）：`BLOCK_SIZE=64, BM=64, BN=64, BK=32,
WM=64, WN=64`。下一步直接**按这组形状钉住 matmul 家族的 tile**（而不是让它按上游逻辑动态选），依据是"性能日志里的
形状是这台机器上真实测过的"，并且在合并期把不确定性降到最低。验收顺序不变：

1. `test-backend-ops -b Vulkan0 -o MUL_MAT` → 2684/2684；
2. `MUL_MAT_ID` / `RMS_NORM` / `SOFT_MAX`；
3. 商品路径 `25,15451,369,279,`；
4. 再谈 stream-K 与上游 stream-K 的对接（性能项，排在正确性之后）。

### 失败按类型分组后的结论：**dense（`mul_mm`）家族整体不对**，`mul_mmq` 正常

把 `test-backend-ops -b Vulkan0 -o MUL_MAT` 的失败按 `type_a × type_b` 分组（控制台输出，按行汇总）：

| 失败族 | 代表用例 | 走的 shader |
| --- | --- | --- |
| `f16 × f32`、`f32 × f32` | `m=100,n=9,k=16`、`m=16,n=16,k=4` 等 | `mul_mm.comp`（dense matmul，`matmul_*` 管线）|
| `q1_0`、`nvfp4` | `m=16,n=16,k=256` | 上游新增的量化类型，本树尚未实现对应分支 |
| 量化 A（`q4_1` 等） | 全部通过 | `mul_mmq.comp` |

也就是说：**`mul_mmq` 那条路是好的，坏的是 dense `matmul_*` 家族**（`mul_mm.comp` + 对应 C++ 派发）。
`q1_0` / `nvfp4` 的失败是"上游新增类型我们还没有内核"，属于后续接入项，不是回归。

因此下一步聚焦 `matmul_*`：先用 `-p` 过滤单个用例（例如 `-o MUL_MAT -p 'type_a=f32.*m=16,n=16,k=4'`）配合
`STRATA_VK_MM_TILE` 固定 warp tile 做对照，确认是 **tile 参数**还是 **K 方向分块 / k_split** 的问题；tile 的取值仍以
`PERFORMANCE-LOG.md` 里本机实测过的形状为准（`BM=64, BN=64, BK=32, WM=64, WN=64`）。

### dense matmul 的 shader 与推常量都与 pre-repin 等价，剩下的是 tile 网格

逐项对照结果：

| 项 | 对照结果 |
| --- | --- |
| `mul_mm.comp` | 与旧钉点相比只有 3 处小改动：参数块条件包含、`ptq1_0.glsl` 包含、一条注释 ⇒ 实际上仍是旧上游那份，pre-repin 是好的 |
| `ggml_vk_matmul` 的 `vk_mat_mat_push_constants` 初始化 | **与 pre-repin 逐字段相同** |
| warp tile 由 `STRATA_VK_MM_TILE` 改动 | 单例错误从 6.44 变成 6.07 ⇒ 误差**依赖分块**，是 tile / 网格层面的问题，不是标量常量错 |

单例复现命令（保留以便后续迭代）：

```
build/bin/test-backend-ops.exe -b Vulkan0 -o MUL_MAT -p 'type_a=f32,type_b=f32,m=100,n=9,k=16'
→ ERR = 6.437 > 5e-4  FAIL   （m=100 与 n=9 都是非整块，k=16 < BK）
```

因此下一步只查一件事：**`wg_denoms`（派发网格）与 shader 里的 `BM/BN` 特化常量是否一致**。两者在
`create_mm_pipelines` 里都来自 `tc.warptile`，合并后若只有一侧按新结构取，就会表现为"网格算得少一半、边缘块算错"。

### dense matmul 在设备上**输出全零**（隔离到 mm-probe 之后）

用仓库里已有的 `mm-probe --verify`（单算子、与 CPU 逐行对照）把问题从模型里剥离出来：

```
mm-probe -b Vulkan0 -t f32 -m 100 -n 9 -k 16 --verify
  row 3: dev 0 cpu 1.34974 ratio +0.0000
  row 4: dev 0 cpu -1.30569 ratio -0.0000
  ...
  9/9 9/9 ...            ← 每一行都是 9/9，即整幅输出都是 0

mm-probe -b CPU -t f32 -m 100 -n 9 -k 16 --verify
  row 5: dev -0.512261 cpu -0.512261 ratio +1.0000
  0/9 0/9 ...            ← CPU 正确
```

也就是说：dense matmul 的**派发没有把结果写进 `d`**（不是数值偏差、不是分块错位），`mul_mmq` 那条路正常。
下一步只需回答"为什么没写"：要么网格为 0/未被记录，要么 shader 的写入绑定点与 C++ 传给它的子缓冲不是同一个
（`{ a, b_chunk, d_chunk }` 三个绑定），要么命中的是 split-k 变体而 C++ 传的是 `d`。`STRATA_VK_PIPELINE_TRACE=1`
与后端自带的派发追踪足以分辨这三种，不需要再改算法。

### dense matmul 的失败面（形状扫描）与已排除项

用 `mm-probe --verify` 做形状扫描，结论很干脆：

| 形状 | 结果 |
| --- | --- |
| `m=8, n=8, k=8` | **正确**（走 `mul_mat_vec` 一类的小形状路径）|
| `m=32, n=32, k=32` | 全零 |
| `m=100, n=9, k=16` | 全零 |
| `m=128, n=64, k=64` | 全零 |

派发追踪（`STRATA_VK_MM_TRACE=1`）显示大形状走的是 `matmul_f32_f32_0`，网格 `(4,1,1)` 正确、`block=1`（用参数块）。

本轮排除的项（都有实验或逐行对照）：

- 管线创建与 SPIR-V 来源：`matmul_f32_f32_cm1`，**与 pre-repin 完全相同**；
- 推常量初始化：`vk_mat_mat_push_constants` 的字段**与 pre-repin 逐字段相同**；
- 参数块路径：`ggml-vulkan-common.h` 里同时写了块内容（memcpy 到 slot）、绑定了动态偏移（`param_dynamic_offset`），
  并且照常 push constants；把 meta 里 `matmul` 的 `param_block` 临时改为 `false` 后结果**仍全零**，已恢复；
- 形状与 tile：改 `STRATA_VK_MM_TILE`（4x2 / 16x8 / 32x8）结果**仍全零**；
- `mul_mm.comp` 的 `PARAM_BLOCK_ENABLED`：生成器会给它定义（不在 `keep_push_constants` 名单里）。

因此剩余疑点收敛为**该 coopmat1 kernel 在本机这条组合上的执行**（特化常量 `MmTypeA`(12) 与 `SHMEM_STRIDE_PAD`(13)
我们只传了 0..11，两者取默认值），以及 `WARP=64`（本机 subgroup）与 `BLOCK_SIZE/WMITER/TM` 的几何一致性。
下一步就用这两个常量做对照：显式传入 `MmTypeA` / `SHMEM_STRIDE_PAD` 并核对 `WMITER*TM == WM`。

### 派发点是哪个函数：追踪放错了位置

`strata-vk` 的 `[mm]` 追踪写在 `ggml_vk_matmul()` 里，但 `mm-probe` 的本机用例**从未触发**它，而 `[disp]` 记录显示
`matmul_f32_f32_0` 确实被派发。也就是说：dense matmul 的这一分支**不经过 `ggml_vk_matmul()`**，而走另一处直接
`ggml_vk_dispatch_pipeline(...)` 的调用点。前几轮"`ggml_vk_matmul` 的推常量与 pre-repin 相同"的对照结论因此只覆盖了
**另一条**分支，不能推广到这条路径——这是本轮必须更正的推理。

已确认的相关事实：

- `matmul_*_cm1` 变体确实由**我们的** `mul_mm.comp` 加 `COOPMAT=1` 生成（生成器 543 行处的 `source_name`），
  所以 shader 侧的改动对它们是生效的；
- cm1 的特化常量列表只有 12 个（对应 `constant_id` 0..11）；`MmTypeA`(12) 与 `SHMEM_STRIDE_PAD`(13) 取 shader 默认值，
  上游对非量化构造器也是这个行为。

下一轮先把 `[mm]` 追踪移到**通用派发**处并带上调用点标记（或直接在每个 `ggml_vk_dispatch_pipeline` 调用点前打印一行），
确认这条路径的推常量是由谁填的，再对照它的字段；在此之前的字段对照结论作废。

### 关掉 coopmat 也仍然是全零：问题不在内核家族

```
GGML_VK_DISABLE_COOPMAT=1 GGML_VK_DISABLE_COOPMAT2=1
mm-probe -b Vulkan0 -t f32 -m 32 -n 32 -k 32 --verify
→ row 2: dev 0 cpu -0.8259 ratio -0.0000      （仍然全零）
```

而 `m=8,n=8,k=8` 是**正确**的（走 `mul_mat_vec` 那条路径）。因此：

- `mul_mat_vec` 一侧正常；
- **dense matmul（`matmul_*`）在 coopmat 开与关两种情况下都写不出结果** ⇒ 与内核家族无关，问题在**派发这一层**
  （子缓冲、网格或 pc 的填写）。

目前已知：`ggml_vk_matmul()` 的追踪从未触发，而 `[disp]` 显示 `matmul_f32_f32_0` 被派发，说明调用点在别处。
代码里 `ggml_vk_mul_mat` 与 `ggml_vk_mul_mat_q_f16` 及其 vec 变体共有多处 `ggml_vk_dispatch_pipeline`，
本轮已排除其中 `mul_mat_vec_p021`（5 绑定）与 `to_fp16`（2 绑定）两处。

下一轮的做法：给 `ggml_vk_dispatch_pipeline` 的追踪加一个**调用点标记**（例如把 `__LINE__` 作为默认参数传入，
或在该函数的每个 matmul 相关调用点前打印一行），一次运行即可锁定那一处，然后只对照它的子缓冲与 pc。

### 追踪位置已确认无误，但结论仍是"没进 ggml_vk_matmul"

`ggml_vk_matmul()` 的第一条语句就是 `[mm]` 追踪（`STRATA_VK_MM_TRACE`），实测**从未打印**；而 `[disp]` 记录显示
`matmul_f32_f32_0` 确实被派发。两者只能同时成立的情况是：这个 `matmul_*` 管线**不是**由 `ggml_vk_matmul()` 派发的。

全文件共有 81 个 `ggml_vk_dispatch_pipeline(...)` 调用点。与"3 个子缓冲 + 一个 pipeline 变量"形态相符的只有
`ggml_vk_matmul()` 内的两处（7192 / 7217 行）。因此剩下的可能是：这条路径用了 **narrow-n 的 `matmul_*` 变体**，而该变体
由别的函数派发（`8438` 的 `dmmv`、`8542` 的 p021、`8636` 的 nc、`9778` 的 `dmmv` 四处里的一处）。

下一轮的做法（一次运行即可定案）：在这四处的调用前各打印一行唯一标记（`site=A/B/C/D`），跑一次 `mm-probe`，
标记与 `[disp]` 的先后顺序会直接指出是哪一处；随后只对照那一处的子缓冲与 pc 填写。

### 派发点的定位进展：管线由 `ggml_vk_guess_matmul_pipeline_map()` 选出

两处使用该函数：

- 7894 行（`ggml_vk_mul_mat_q_f16`，dense matmul）：`vk_pipeline pipeline = ggml_vk_guess_matmul_pipeline_map(ctx, *mmp_map, ne01, ne11, aligned, false);`
- 9299 行（`ggml_vk_mul_mat_id_q_f16`，专家 matmul）

对应 `align_map` 决定 `kpad`。这也解释了命中 `matmul_f32_f32_aligned_0` 的原因：`aligned == true` 时选的就是
`configs[idx].aligned`。

下一轮在这两处之后各加一个标记，并在**每一处可能消费该 `pipeline` 的派发点**（含 8062 行附近的 `ggml_vk_matmul` 调用）
之前打印同样带行号的标记，一次运行即可确认实际执行的是哪一条分支；届时再对照该分支的子缓冲与 pc。

### 本端口四种类型的失败形态：matvec 近似正确，matmul 全零

`mm-probe --verify` 对 `tqk6`（`tqk7` / `tq2_t` / `ptq1_0` 同形）的三种形状：

| 形状 | 结果 |
| --- | --- |
| `m=256, n=1, k=256` | `nmse 1.5e-05`，首行 `dev 5.67027` vs `cpu 5.68232` ⇒ **近似正确**（走 matvec）|
| `m=16, n=64, k=256` | 全零（`dev 0`）|
| `m=256, n=256, k=256` | 全零（`dev 0`）|

而对照类型 `q4_1` 在 `m=16,n=9,k=256` 下 `nmse 2.4e-14`，说明探针与 harness 本身没问题。

kernels 对照（与 pre-repin 逐字节比较）：`mul_mat_vec.comp`、`mul_mat_vec_base.glsl`、`dequant_funcs.glsl`、
`mul_mmq_funcs.glsl` **完全相同**；只有 `mul_mm_funcs.glsl` 不同（我们新增的 `ptq1_0.glsl` 包含）。

因此最可能的解释是：`n > 1` 时这些类型被路由到 **coopmat 的 dense matmul**，而 coopmat 的 A 载入路径
（`coopmat_stage` / `APPLY_SLM_A_RESHAPE`）没有我们这四种类型的分支，累加器恒为零；`n == 1` 走 matvec，
用的是我们已经验证过的类型分支，所以只有小幅数值差。

下一步：把这些类型从 coopmat matmul 的管线映射里排除（让它们走 dequant→f16 或 matvec 路径），
用 `mm-probe` 三种形状复核；之后再单独核对 matvec 那 1.5e-05 的偏差是否在既有容差之内。

### 四种本端口类型是从哪条路径拿到 dense matmul 管线的

`FOR_EACH_TRELLIS_TYPE`（`ggml-vulkan.cpp` 2872 行）定义了 `PTQ1_0 / TQ2_T / TQK6 / TQK7`，它只被
`FOR_EACH_LUT_TYPE` 展开一次（2880 行），注释写的是"join the scalar and coopmat1 expansions"。

实测说明这句话对 coopmat1 **不成立**：`mm-probe -t tqk6` 在 `n > 1` 时全零（走 cm1 dense matmul），`n == 1` 时近似正确
（走 matvec）。也就是说 trellis 类型确实拿到了 cm1 管线，而 `mul_mm.comp` 的 coopmat 载入路径（`coopmat_stage` /
`APPLY_SLM_A_RESHAPE`）里没有这四种类型的分支，累加器恒为零。

下一步有两条，取其一并写清理由：

1. 把 trellis 类型从 **coopmat1 的 matmul 管线**里排除（保留标量 / matvec / mmq 路径），与注释"solo scalar"一致；
2. 或者给 `mul_mm.comp` 的 coopmat 载入路径补上四种类型的分支（工作量大，且要先确认 coopmat 的 A 布局约束）。

考虑到 B 项用的是 Q3_K 与 TQ 系列、且 matvec 路径已经验证可用，第 1 条先用 `mm-probe` 的三种形状验证，再决定是否需要第 2 条。

### trellis 类型走的是 LUT matmul（不是 coopmat），网格与定义都正确

派发追踪（`STRATA_VK_MM_TRACE=1`，`-t tqk6 -m 16 -n 64 -k 256`）：

```
[disp] matmul_tqk6_f32_aligned_0 wg=(1,2,1) block=1
[mm]   matmul_tqk6_f32_aligned_0 m=16 n=64 k=256 split_k=1 batch=1 wg_denoms=(32,32,1) grid=(1,2,1)
```

因此上一轮把原因归到"coopmat 载入路径"是不准确的：它走的是 **LUT 类型的普通 matmul**（`mul_mm.comp` 以
`DATA_A_TQK6` 等定义生成），网格 `(1,2,1)` 对 `m=16,n=64,BM=BN=32` 来说正确，管线名与 `wg_denoms` 也一致。

生成器侧也确认无误：`data_a_key = "DATA_A_" + to_uppercase(tname)`，`tqk6 → DATA_A_TQK6` 会被定义；
`lut_load_vec_a()` 对本端口类型返回 `"8"`。

于是问题收敛到 `mul_mm_funcs.glsl` 中这四种类型的 `load_a` 分支本身（最可能与本机 tile 的 `BK=16` 有关：
该分支按每 8 个权重一组、假设了某个 `BK` 下限）。下一轮按既有最快手段处理：**把该分支手抄成 Python，
与已验证的解码器（`port/tools/q3k-check.py` 一类的独立实现）逐值 diff**，定位偏移或位序错误后再改 shader。

### trellis 的 matmul 载入分支读的是 `data_a_packed16`（binding 0）

`mul_mm_funcs.glsl` 的四条类型分支都用 2 字节对齐的 packed 结构：

```glsl
#elif defined(DATA_A_TQK6) || defined(DATA_A_TQK7)
const uint idx = pos_a + col * p.stride_a / LOAD_VEC_A + row;
const uint ib  = idx / 16;
const uint t0  = (idx & 0xfu) * 2u;
const float d  = float(data_a_packed16[ib].d);
```

`data_a_packed16` 在 `mul_mm.comp` 里声明在 **binding 0**（与主 A 缓冲互斥），所以"绑定缺失"可以排除；
`types.glsl` 也确有 `block_tqk6_packed16` / `block_tqk7_packed16` 类型。

剩下要核对的只有**索引算术**：`p.stride_a` 由 C++ 以**元素**为单位传入，而 packed16 结构把 16 位字段按 u16vec 解释，
`LOAD_VEC_A = 8` 时每线程取 8 个权重、每块 16 个 8 元组。若 `stride_a / LOAD_VEC_A` 与实际的块步长差一个因子，
`ib` 会指到错误的块（读出零或错值）。

下一轮把这段分支手抄成 Python，用 `port/tools/q3k-check.py` 那类已验证解码器逐值对照，确定 `stride_a` 与
`ib`/`t0` 的正确关系后再改 shader；`mm-probe -t tqk6` 的 `n=1 / 64 / 256` 三种形状作为回归判据。

### 找到 `q1_0` / `nvfp4` 写零的直接原因：`MmTypeA` 没有作为特化常量传进去

管线追踪（`STRATA_VK_PIPELINE_TRACE=1`，`-t q1_0 -m 16 -n 64 -k 256`）：

```
[disp] matmul_quant_f32_aligned_0
[pipe] matmul_quant_f32_f16acc_0  spec=[64,32,32,32,32,32,2,8,8,1,64,0]
```

特化常量只有 **12 个**（`constant_id` 0..11）。而 `mul_mm_funcs.glsl` 的通用量化分支是按
`if (MmTypeA == GGML_TYPE_Q4_0) … else if (MmTypeA == GGML_TYPE_Q1_0) …` 在**运行时**选类型的，`MmTypeA` 是
`constant_id = 12`。它没被传入，取默认值 `0`，于是整条链都不匹配、内核写不出结果——这正是 `q1_0` / `nvfp4` 全零的机制。

对照：`iq4_xs` / `q4_K` / `q6_K` 在同一形状下 `nmse ≈ 2.7e-05`（走各自编译期的类型分支），`mxfp4` 更是 `1.8e-15`，
所以这条"通用量化 matmul"只对依赖 `MmTypeA` 的那批类型失效。

下一轮：在这些管线的创建处补上 `MmTypeA`（与 `ggml_vk_mul_mm_spec_quant` 一致，追加 `type` 与 `SHMEM_STRIDE_PAD`
两个常量），然后用 `mm-probe -t q1_0 / nvfp4` 复核，再跑 `MUL_MAT` 全量。

### 更正：`MmTypeA` 其实是传进去了（是我自己的追踪截断造成的误判）

上一节说"通用量化 matmul 没收到 `MmTypeA`"，依据是追踪只打印 12 个特化常量。把追踪上限从 12 提到 20 后：

```
[pipe] matmul_quant_f32_f16acc_aligned_0 wg_denoms=(32,32,1)
       spec=[64,32,32,32,32,32,2,8,8,1,64,1,41]
                                             ↑ ALIGNED=1, MmTypeA=41=GGML_TYPE_Q1_0
```

也就是说 `MmTypeA` 一直是正确的——上一轮结论作废。追踪上限已改为 20 并保留，免得同类误判再发生。

于是 `q1_0` / `nvfp4` 写零的原因在别处：常量对了、`mul_mm_funcs.glsl` 里也确有
`else if (MmTypeA == GGML_TYPE_Q1_0)`（505 行）与对应分支。剩下要查的是这条**运行时分支里读的结构体**
（`a_q1_0_p16` 之类）在通用管线里是否被正确定义/绑定——即 `A_TYPE_PACKED16` 为通用量化类型时选的是哪个结构。
下一轮先用同样的"常量替换"探针确认这条分支确实执行，再查它读的缓冲。

### `q1_0` 的三块拼图都对得上，问题缩小到 `mm_load_vec_a()` 与 `p.stride_a`

逐项核对（`q1_0` 走 `matmul_quant_f32_f16acc_*`，即 `mul_mm.comp` 的 `MULMAT_QUANT` 通用量化分支）：

| 项 | 状态 |
| --- | --- |
| 特化常量 `MmTypeA` | `spec=[…, 64, 1, 41]` ⇒ 41 = `GGML_TYPE_Q1_0` ✓ |
| 缓冲声明 | `mul_mm.comp:98` 有 `layout (binding = 0) … a_q1_0` ✓ |
| 块布局 | `types.glsl` 的 `block_q1_0 {float16_t d; uint8_t qs[16];}` 与 `ggml-common.h` 的 `{ggml_half d; uint8_t qs[QK1_0/8];}` 一致 ✓ |
| 分支本体 | `mul_mm_funcs.glsl:505` 的 `else if (MmTypeA == GGML_TYPE_Q1_0)` 按位取 ±d ✓ |

剩下两个量还没核对：分支里的 `mm_load_vec_a()` 与 `p.stride_a` 的单位。若 `mm_load_vec_a()` 与
该变体的 `LOAD_VEC_A` 不一致，`idx`/`k_pair` 就会落到块外，读到的正好是零（`d = 0` 时 ±0 相加仍是 0，与"精确的全零"吻合）。

下一轮：打印/断言 `mm_load_vec_a()` 与 `LOAD_VEC_A` 的关系，并核对通用量化路径下 `p.stride_a` 的传入单位；
必要时让 `q1_0` 走**编译期分支**（`DATA_A_Q1_0` 的 typed 变体）验证是"运行时链"还是"索引"的问题。

### `q1_0`：被派发的管线确实带着 `MmTypeA = 41`

追踪的是**真正被派发**的那条（`matmul_quant_f32_aligned_0`，f32 累加，不是 `_f16acc`）：

```
[pipe] matmul_quant_f32_aligned_0 wg_denoms=(32,32,1) spec=[64,32,32,32,32,32,2,8,8,1,64,1,41]
[pipe] matmul_quant_f32_aligned_0 wg_denoms=(32,32,1) spec=[64,32,32,32,32,32,2,8,8,1,64,1,42]
```

`constant_id = 12` 依次是 41（`Q1_0`）与 42（同一次运行里另一条类型）。`ggml_vk_create_pipeline` 的
`SpecializationMapEntry` 按 `specialization_constants.size()` 分配，没有 12 项上限，所以第 13 个常量确实进了管线。

于是"常量缺失"这条彻底排除。剩下的可能只有两种，都用**同一支探针**就能分清：

1. 分支执行了，但 `store_a` 写进共享内存的位置不是乘加读取的位置（`a_shmem_index` / `SHMEM_STRIDE` / `APPLY_SLM_A_RESHAPE` 三者不一致）；
2. 分支没执行（`MmTypeA` 在 shader 侧仍是 0），而管线 spec 显示 41。

探针做法：把 `else if (MmTypeA == GGML_TYPE_Q1_0)` 分支体改成无条件 `store_a(..., 1.0)`。若输出变成非零 ⇒ 分支执行、
问题在读取侧；若仍是零 ⇒ 分支没执行，要去查 `MULMAT_QUANT` 的常量声明与 `ggml_type_ids.glsl` 的包含顺序。

### `q1_0` 与 `q4_1` / `q5_1` 走同一条通用量化路径，却只有 `q1_0` 是零

同一形状（`m=16,n=64,k=128`）的对照：

| 类型 | nmse |
| --- | --- |
| `q5_1` | **2.1e-14**（精确）|
| `q4_1` | **1.2e-14**（精确）|
| `q1_0` | 1.0（全零）|

三者都在 `non_lut_quant_types` 里，都走 `matmul_quant_f32_*`，都靠 `MmTypeA` 在运行时选分支，`mm_load_vec_a()`
对三者都返回 8。所以问题不在"通用路径整体坏了"，而在 `q1_0` 这一支本身。

另外做了一次"常量替换"探针：把 `MmTypeA == GGML_TYPE_Q1_0` 分支体改成无条件
`store_a(..., 1.0)`，输出**仍然是零**。这说明该分支根本没有被执行——即命中的是**另一个**源文件里的分支实现
（管线用的是 `matmul_quant_f32_cm1_*` 这一组 SPIR-V，可能来自 coopmat1 的专用源/分支，而不是
`mul_mm_funcs.glsl` 里 `#else` 的那条运行时链）。

下一轮先确认一点：`matmul_quant_f32_cm1_*` 的 SPIR-V 由哪个源文件生成（`mul_mm.comp` + `COOPMAT`，还是单独的
`mul_mm_cm1.comp`），以及那个源里的 A 载入分支覆盖了哪些 `MmTypeA`；`q1_0` 若不在其中，就补上或把它挪到已验证的路径。

### `q4_1` / `q5_1` 走的是 mmq，`q1_0` 走的是通用量化 matmul

派发追踪显示 `q4_1` 会先跑 `quantize_q8_1_x4`（整数点积的 mmq 路径，结果精确到 1e-14），而 `q1_0` 直接跑
`matmul_quant_f32_aligned_0`。也就是说两者并不在同一条路上——上一节"同一条通用路径"的说法需要更正：
`q4_1` / `q5_1` 有 mmq 内核，`q1_0` 没有，所以只有它落到通用量化 matmul。

生成器侧也确认了：`matmul_quant_f32` 由 `mul_mm.comp` 加 `MULMAT_QUANT=1` 生成（`source_name` 就是 `mul_mm.comp`），
而 `is_lut_quant()` 对 `nvfp4` 为真、对 `q1_0` 为假，所以两者分别走 typed LUT 变体与通用变体。

据此，下一次探针应放在**函数入口**而不是分支内部：在 `load_a_to_shmem` 开头无条件
`store_a(col, row * LOAD_VEC_A_EFF / 2, FLOAT_TYPEV2(1.0, 1.0))`（对所有类型生效），然后分别测 `q1_0` 与 `q4_1`：

- 若 `q1_0` 变为非零 ⇒ 分支链没被走到（要查 `#else` 链的守卫条件）；
- 若仍为零 ⇒ 问题在累加/写回（`store_d`）而不是载入。

### `q1_0` 记录项：下一步探针的位置要改

尝试在 `load_a_to_shmem` 入口无条件 `store_a(...)` 作为探针，但**编译失败**：`LOAD_VEC_A_EFF` 是
`mul_mm.comp` 里 `main()` 的局部常量，`mul_mm_funcs.glsl` 里看不到它；同一位置 `store_a` 也不在作用域内
（探针被插到了定义之前）。探针已回退，构建恢复绿色（`q4_1` 仍为 1.2e-14）。

下一轮的探针应改成：

```glsl
// 放在 load_a_to_shmem 的函数体内、store_a 定义之后，且只依赖函数参数与 mm_load_vec_a()
store_a(col, (row * mm_load_vec_a()) / 2, FLOAT_TYPEV2(1.0, 1.0));
```

若 `q1_0` 因此变为非零 ⇒ 类型链未走到；仍为零 ⇒ 问题在累加或 `store_d`。

### 当前状态小结（避免后续重复排查）

- `q1_0` / `nvfp4`：上游新增类型，**写零**，已限定到"通用量化 matmul / typed LUT matmul"两条路；
- 本端口四种类型（`PTQ1_0 / TQ2_T / TQK6 / TQK7`）：已从写零的 matmul 路径挪开，近似精度 `~1.4e-05`，可用；
- `MUL_MAT` 全量：**2427/2684**（修复 `WNITER = 0` 之后从 2065 提升）；
- 商品路径仍是 `47464,136140,0,0,`（期望 `25,15451,369,279,`），下一步应换到算子级排查（`RMS_NORM` / `SOFT_MAX` / `FLASH_ATTN` / `MUL_MAT_ID`）。

### 新发现：`MUL_MAT_ID` 跑完全部用例后**在清理阶段崩溃**

单算子跑（`-b Vulkan0 -o MUL_MAT_ID`）25 条用例全部打印 `OK`，随后进程以 `0xC0000005`（访问冲突）结束，
连 `N/N tests passed` 摘要都没打印。`MUL_MAT` 的全量跑能正常打印摘要，所以这条崩溃与 **`MUL_MAT_ID` 留下的状态**有关，
发生在 teardown（销毁 device / 释放缓冲）而不是计算阶段。

同一现象也出现在 `GET_ROWS`（同样只打印 OK、无摘要）。两者共同点：都用到 `ggml_vk_mul_mat_id` 相关路径与
`expert_count` / `row_ids` 缓冲。

这与之前偶发的 `0xC0000409`（`vk::Queue::submit: ErrorInitializationFailed`）不同：那是提交阶段，这次是清理阶段。
对用户可见的影响是"服务结束/切换模型时可能崩溃"，属于 A 项要修的 incompatible。

下一轮：用最小复现（`-o MUL_MAT_ID` 单跑）配合逐段释放顺序核对，重点看：
1. `expert_count_buf` 这类按图分配、在 `ggml_vk_mul_mat_id` 里申请的缓冲是否在 teardown 前被释放；
2. 我们的参数块缓冲（`ctx->param_block`）与描述符集在 device 销毁前是否已释放；
3. `MUL_MAT_ID` 是否把某个 `vk_pipeline` 的 `wg_denoms` 写坏，导致后续释放越界。

### teardown 崩溃的两个边界事实

| 运行 | 退出码 |
| --- | --- |
| `-b CPU -o MUL_MAT_ID` | **0**（正常，1288 行输出，含 `3/3 backends passed`）|
| `-b Vulkan0 -o MUL_MAT_ID` | `0xC0000005`（25 条用例全 OK，随后崩）|
| `-b Vulkan0 -o MUL_MAT_ID` + `GGML_VK_DISABLE_COOPMAT{,2}=1` | 仍 `0xC0000005` |

⇒ 崩溃是 **Vulkan 后端特有**、且**与 cooperative matrix 无关**；CPU 侧同一套用例完全正常，说明问题在后端自己的状态/释放，
不在测试或模型代码。

下一轮的做法：在后端释放路径加**环境变量守卫的逐步打印**（例如 `STRATA_VK_TEARDOWN_TRACE=1` 时在
`ggml_backend_vk_free`、`ggml_vk_device_destroy`、参数块缓冲与描述符集释放之间各打一行），跑一次
`-b Vulkan0 -o MUL_MAT_ID` 即可看出停在哪一步。这比继续读代码更快。

### `MUL_MAT_ID` 的秒级复现：崩在 `ggml_backend_alloc_ctx_tensors` 内部

复现命令（几秒）：

```
mm-probe -b Vulkan0 -t q4_K -m 72 -n 16 -k 2048 --n-as 4 --n-used 2
→ exit = 0xC0000005
```

`MM_PROBE_TRACE=1` 时探针在关键步骤打印，最后一次输出是：

```
[probe] expert_setup          ← 三个张量（as / b / ids）已建好
[probe] alloc_ctx_tensors     ← 进入 ggml_backend_alloc_ctx_tensors
（随后访问冲突）
```

也就是说：**崩溃在缓冲区分配阶段**，既不是计算、也不是 teardown。此前 `test-backend-ops -o MUL_MAT_ID` 的 25 条用例能跑完，
说明它的分配路径（`ggml_backend_alloc_buffer` + `set_usage`）不受影响，而 `ggml_backend_alloc_ctx_tensors` 这条会崩。

下一轮：在 `ggml_backend_vk_buffer_type_alloc_buffer` / `ggml_backend_vk_buffer_type_get_alloc_size` 入口各加一行打印，
跑同一命令，看崩溃发生在"进入分配前"（说明是 `ggml.c` 的 `alloc_ctx_tensors` 遍历张量时踩到坏元数据）
还是"进入之后"（说明是我们的 buffer 实现）。

### `MUL_MAT_ID` 的崩溃与专家数有关（4 / 16 崩，128 干净）

同一算子按用例子集跑：

| 过滤 | 结果 |
| --- | --- |
| `-p n_mats=4` | 15 行输出后 `0xC0000005` |
| `-p n_mats=16` | 15 行输出后 `0xC0000005` |
| `-p n_mats=128` | **退出码 0**，`2/2 tests passed` |

⇒ 崩溃与 `n_as`（专家数）相关，而不是"跑完必崩"。这条比之前所有结论都更具体。

相关代码位置（`ggml_vk_mul_mat_id`）：

```cpp
const uint64_t max_tiles      = ggml_vk_mul_mat_id_max_tiles(n_as, nei0 * nei1, bn);
const uint64_t row_ids_offset = 1 + 2 * max_tiles;
const uint64_t row_map_words  = row_ids_offset + max_tiles * bn;
const size_t   expert_data_size = sizeof(uint32_t) * row_map_words;   // 写进 ctx->prealloc_split_k
```

而 `row_ids`（u16vec2 × BN）在共享内存里，静态大小；`expert_count` 写进 `prealloc_split_k`。当 `max_tiles` 被低估时，
`count_experts` 会写到 `prealloc_split_k` 末尾之外 → 堆被写坏 → 之后任意位置爆掉，且**只在专家数少的用例**上出现
（`max_tiles` 随 `n_as` 变化的拐点正好在这附近）。

下一轮：

1. 用 `-p n_mats=8 / 32 / 64` 找出崩与不崩的分界；
2. 把 `ggml_vk_mul_mat_id_max_tiles()` 的返回值与 `count_experts.comp` 实际写入量逐项核对（`1 + 2*max_tiles` 头部 + 每 tile 的 `bn` 个 row 映射）；
3. 修正界或按上界多分配一个 tile，用同一组 `-p` 验证退出码。

### `MUL_MAT_ID` 崩溃的定性：**只出现在测试台**，引擎侧不复现

| 运行 | 结果 |
| --- | --- |
| `test-backend-ops -b Vulkan0 -o MUL_MAT_ID`（整套，重复 3 次）| 每次都 `0xC0000005`，稳定复现 |
| `strata-vk --native Qwen3.8-Flash-Next-Q2 … --n 16`（真 MoE 负载）| **exit 0**，16 个 token 正常走完 |

环境里没有可用的调试器（无 `cdb`/`windbg`），DLL 也没有导出符号/PDB，所以拿不到调用栈。综合这些：
该崩溃在测试台的"多用例复用同一 backend + 大量缓冲反复分配释放"模式下触发，**引擎侧不出现**。

因此把它降级为**已记录问题**（带复现命令），不再占用主线；主线回到两件真正影响可用性的事：

2. B 项尚未启动的部分（前端接线 / PLE 转换 / MTP / 下载策略）。

### 商品路径下一步：用现成的逐节点 dump 做二分

引擎已有 `STRATA_VK_EVAL=<substring>`（`port/engine` 里，注释写明"按节点名过滤、打印每个节点的 checksum，用来逐节点比较
CPU 与 Vulkan 路径"）。这正是当前需要的工具：

1. 同一 prompt、同一模型，分别用 `--gpu cpu` 与默认 Vulkan 跑，`STRATA_VK_EVAL` 设一个覆盖面足够的名字（或先
   `STRATA_VK_EVAL_GRAPH=1` 把图打出来选名字）；
2. 把两份 checksum 列表按节点名对齐比较；
3. **第一个不一致的节点**就是坏算子，随后用 `mm-probe` / 单独用例隔离并修。

这比继续在"整条链输出 47464,136140,0,0"上猜要快得多。

1. Vulkan 侧在 `STRATA_VK_EVAL=all`（每节点一次读回）下跑到第 3 层就

2. 比较脚本已固化为 `port/tools/node-diff.py`（输入两份 `[eval]` 文本，输出共同节点里的最大相对差）。

下一轮：先跑 `test-backend-ops -o 'DSV4_HC_PRE,DSV4_HC_POST'` 看这两个算子是否被现有用例覆盖，
再对照 `dsv4_hc_pre.comp` 与 CPU 参考实现（`ggml-cpu/ops.cpp` 里的对应实现）逐项核对。

### 重要更正：`DSV4_HC_PRE` 的 21 倍差**可能是比较方法的伪影**

`port/tools/node-diff.py` 目前把节点名当作唯一键（`dict.setdefault`，保留第一次出现）。但实际上：一次运行里有**多次 graph compute**
（prefill、decode，以及可能的 warmup），同一节点名会出现多次、值不同。两次运行的次数或顺序一旦不同，就会把
"prefill 的值"与"decode 的值"拿来比 —— 21 倍这种量级差正是这种错配会给出的结果。

而算子自测是**通过**的：

```
test-backend-ops -b Vulkan0 -o DSV4_HC_PRE,DSV4_HC_POST  → 17/17 tests passed
（含 n_embd=1, n_hc=4, n_tokens=1 的 decode 形状，以及 gated 变体；n_hc != 4 标记为 not supported）
```

因此下一步必须先修比较工具，再谈结论：

1. 解析时保留**出现序号**，按 `(name, op, n, occurrence)` 对齐后逐项比较；
2. 或者只比较**单次 graph compute** 的节点（在 dump 里插入 graph 边界标记，或在每次 compute 后清空）。

修好后再重跑 CPU/Vulkan 两份 dump，得到的第一个真正分歧节点才可信。在此之前"坏算子是 `DSV4_HC_PRE`"这一结论**不成立**。

### `GATED_DELTA_NET`：字段错位已修，但该用例现在改为崩溃

也就是说：错位掩盖了第二个问题。现在的行为说明 magic 除法与 stride 都读对了，内核真正开始按正确参数工作，
然后在这组参数下越界或触发提交失败。

下一轮要查的是 `gated_delta_net.comp` 在 `n_tokens == 1`（以及 `n_pend == 0`）时的写入范围：

2. `rq3` 的商与余数在 `n_seqs == 1` 时的取值（`rq3 = ne3 / ne_q3`），确认没有除零或商为 0 时的退化路径；
3. 用 `GATED_DELTA_NET` 的其它用例（不同 `n_seq_tokens`）逐条跑，确定是否只有单 token 触发。

### `GATED_DELTA_NET` 的崩溃位置：单条派发之后

`STRATA_VK_MM_TRACE=1` 下，用例 `head_count=32, head_size=128, n_seq_tokens=1, n_seqs=1` 依次派发：

```
[disp] l2_norm_f32           wg=(32,1,1)
[disp] l2_norm_f32           wg=(32,1,1)
[disp] gated_delta_net_f32_d128  wg=(32,1,16)
[disp] l2_norm_f32           wg=(8,1,1)
（随后 0xC0000409）
```

⇒ 崩溃发生在 `gated_delta_net_f32_d128` 这条派发（或紧随其后的提交）上，与 token 数无关
（`n_seq_tokens=1/4` 都崩）。

shader 里唯一可能越界的是状态槽写入：

```glsl
const uint state_size_per_snap = state_size * H * n_seqs;      // state_size = S_V*S_V
const uint slot_base = s_off + uint(target_slot) * state_size_per_snap + state_out_base;
```

而 `s_off` 在"状态写回 dst 尾部"这条路上等于 `S_v*H*n_tokens*n_seqs`。下一轮核对 `target_slot` 的上界
（是否可能取到 `K`）与 `dst` 实际容量（attention 部分 + `K` 个槽）是否一致——若 `target_slot` 能等于 `K`，
就会写到 `dst` 之外。

### 更正：`slot_base` 没有重复计 H；剩余嫌疑在设备侧

上一节说 `state_size_per_snap` 与 `state_out_base` 重复乘了 `H`。逐行读过之后这条不成立：

```glsl
const uint state_out_base      = (seq_id * H + head_id) * state_size;   // 一个槽内某 (seq,head) 的偏移
const uint state_size_per_snap = state_size * H * n_seqs;              // 整个槽的大小
const uint slot_base = s_off + uint(target_slot) * state_size_per_snap + state_out_base;
```

两者分别是"槽内偏移"和"槽大小"，相加是对的；写入还带 `target_slot < K` 的守卫。

同时核对了流水线创建：特化常量 `{S_V, kda, g_subgroup_size, lanes_per_column, lanes_shift}` 正好对应 shader 的
`constant_id` 0..4；`wg_denoms = {1,1,cols_per_wg}` 与观测到的网格 `(32,1,16)` 一致。

所以现在没有指向具体越界的静态证据，只剩下"设备侧执行本身出错"。下一轮换成让 Vulkan 验证层真正生效：

### 第二个 token 的根因症状：**25 / 96 层 MoE logits 变成 NaN**（CPU 同层全部有限）

### NaN 出现在 `hc_mixed` 之后、`ffn_moe_logits` 之内——即 bf16 路由器矩阵乘

25/96 层变 NaN。输入有限、结果 NaN，说明问题在内核本身（例如累加/转换路径），且与输入的具体数值有关。

2. 若通过，则用 `hc-probe` 的方式写一个小探针，把**真实**的 `hc_mixed`（从 eval dump 取那几个 NaN 层的输入）喂给同一个
   `blk.*.ffn_gate_inp.weight` 形状的 bf16 matmul，复现 NaN 并定位内核分支；
3. 修好后以第二 token 的 `ffn_moe_logits` 无 NaN 为门禁。

### 商品路径 NaN 的真正来源：**`CPY` 到量化目标类型是错的**

按 KV 类型逐项对照（两 token，`STRATA_VK_EVAL=ffn_moe_logits`）：

| 配置 | 第二 token 的 NaN | 输出 token |
| --- | --- | --- |
| `--kv q4_0 --flash-attn on` | **25 / 96** | `25,0,0` |
| `--kv q4_0 --flash-attn off` | 0 / 96 | `25,15767` |
| `--kv f16 --flash-attn off` | 0 / 96 | `25,15767` |
| `--kv q8_0 --flash-attn on` | 0 / 96 | `25,3437`（**与 CPU 一致**）|

⇒ 只有 `q4_0` **且** 开 flash-attn 时出现 NaN。而 flash-attn 自身对 q4_0/q4_0 的用例是 **85/85 通过**（测试台直接以目标类型构造输入，不经过设备端量化）。

罪魁是写 KV 缓存那一步——`CPY` 到量化目标：

```
test-backend-ops -b Vulkan0 -o CPY  → 254/271 passed，20 条失败
失败分布：dst=q4_0 ×3、q4_1 ×2、q5_0 ×2、q5_1 ×2、q8_0 ×2 …
ERR ≈ 2.0（相对误差 ~100%，等于整块写错）
```

即 `f32 → 量化` 的拷贝在内核侧写坏了（尺度/块布局），KV 缓存因此是垃圾，flash-attn 读进去就出 NaN，再经路由器矩阵乘扩散成 25 层 NaN。

下一轮：拿 `copy_to_quant.comp`（以及主机侧 `ggml_vk_cpy` 的选择逻辑）与 CPU 参考 `ggml_compute_forward_dup_bytes` 对照，
先看单个 block 的 scale/量化值，用 `-p 'type_dst=q4_0'` 的失败用例作为门禁。

### `CPY → 量化` 的失败点：主机按"块数"算网格，shader 按"元素数"算索引

失败用例是最简单的连续拷贝（`type_src=f32,type_dst=q4_0,ne_src=[256,4,4,4],permute 全 0,_src_transpose=0`，ERR≈2）。

主机侧（`ggml-vulkan.cpp:11903`）：

```cpp
if (op == GGML_OP_CPY && !ggml_is_quantized(src0->type) && ggml_is_quantized(dst->type)) {
    ne = CEIL_DIV(ne, ggml_blck_size(dst->type));   // ← 网格按"块数"算
}
```

shader 侧（`copy_to_quant.comp`，非 SET_ROWS 分支）：

```glsl
const uint idx = (...) * QUANT_K;      // ← 索引按"元素数"推进
if (idx >= p.ne) { return; }
```

两边的单位不一致：主机把 `ne` 折成块数后决定网格，shader 却拿"元素索引"去比 `p.ne`。当 `p.ne` 是元素数时，网格只有
`元素数/32` 个 item，shader 立刻在 `idx >= p.ne` 处返回大半——只有开头若干块被写对，其余是垃圾（ERR≈2）。

下一轮：确认 `p.ne` 的单位（`ggml_nelements(dst)` 还是块数），二选一统一：

1. 若 `p.ne` 是元素数 → 去掉主机的 `/ blck`，让网格覆盖 `CEIL_DIV(ne, QUANT_K * BLOCK_SIZE)`；
2. 若 `p.ne` 是块数 → 把 shader 的 `idx` 改成块索引、`quantize` 内自行乘 `QUANT_K`。

改完用 `-o CPY -p 'type_dst=q4_0'` 作为门禁（当前 3 条失败），再回 `--kv q4_0 --flash-attn on` 验证第二 token。

### `CPY → 量化`：网格按块数、shader 的 `idx` 按元素数，`p.ne` 的单位是判据

主机侧（11887–11905）：

```cpp
uint32_t ne = ggml_nelements(dst);
...
if (op == CPY && !quantized(src0) && quantized(dst)) {
    ne = CEIL_DIV(ne, ggml_blck_size(dst->type));   // 网格：块数
}
```

shader 侧（`copy_to_quant.comp`）：

```glsl
const uint idx = ((z<<18) + (y<<9) + x*32 + lid) * QUANT_K;   // idx 是元素索引
if (idx >= p.ne) { return; }
```

两者只有在 `p.ne == ggml_nelements(dst)`（元素数）时才自洽。如果 `p.ne` 实际是**块数**，那么
`idx >= p.ne` 会在元素 512 附近（= 第 16 块）就返回，只有开头十几块被写对、其余保持原值——与观测到的 ERR≈2 完全一致。

下一轮：在 CPY 派发处打印一次 `p.ne`、`ggml_nelements(dst)`、`dst->type` 与最终的 `elements`，确定 `p.ne` 的单位后，
只改一处（要么 `p.ne` 用元素数，要么 shader 用块索引），然后用 `-p 'type_dst=q4_0'` 验证。

### 试验被否：把目的端 stride 换成"块数"没有改善（已回退）

按"`dst_idx` 返回字节偏移却当块索引用"的猜想，在 `ggml_vk_cpy` 里把 `p.nb10..13` 除以 `ggml_type_size(dst->type)`：

```
test-backend-ops -b Vulkan0 -o CPY → 仍 254/271 passed（20 条失败，与改前完全相同）
```

⇒ 该猜想不成立，改动已回退（`dirty: 0`）。原因在 shader 侧很清楚：非 SET_ROWS 分支用的是专门的
`dst_idx_quant(idx, QUANT_K)`（`generic_unary_head.glsl:72`），字节/块的换算本来就在那里处理，主机端不需要再做一次。

下一轮从正确的位置查：

1. 读 `dst_idx_quant` 的实现，核对它与主机传入的 `p.ne`、`nb1x`、`aoffset/doffset` 的单位关系；
2. 在 CPY 派发处打印一次失败用例的 `p.ne`、`elements`、`p.nb10..13`、`wg_denoms`，与 shader 里的算式逐项对照；
3. 仍以 `-o CPY -p 'type_dst=q4_0'` 作为门禁。

### `CPY → q4_0`：管线与网格都对，仍有 3 个形状失败

派发追踪（`-o CPY -p 'type_dst=q4_0'`）：

```
[disp] cpy_f32_q4_0 wg=(16,1,1)   ← ne=[256,4,4,4]，512 块 / 32 = 16 ✓
[disp] cpy_f32_q4_0 wg=(6,1,1)
[disp] cpy_f32_q4_0 wg=(1,1,1)
9/12 tests passed
```

失败的三个形状：

| 形状 | 备注 |
| --- | --- |
| `ne_src=[256,4,4,4]` | 连续，16 个工作组 |
| `ne_src=[256,2,3,4]` | 源带 permute |
| `ne_src=[96,1,1,1]` | 只有 3 个块 |

逐项核对后，管线选择（`cpy_f32_q4_0`）、`wg_denoms={32,1,1}`、`p.ne`（元素数）、
`dst_idx_quant(idx, QUANT_K)` 的块索引换算、`nb1x`（`dst->nb[x]/type_size`，即块单位）**全部自洽**，
但结果仍然差了约 100%。

所以问题不在索引，而在**写进去的内容**。下一轮直接取回目的端前几个块的原始字节：

1. 用一个小 probe（或在 harness 里临时加一行）把 `dst` 的 `block_q4_0[0..2]` 读回，与 CPU 参考的同一块逐字节比对，
   看是 `d` 为 0、`qs` 全 0，还是只有前 16 字节对（打包错位）；
2. 这一步能区分"没写"、"只写了 `d`"、"nibble 打包错"三种情况，随后按对应分支修。

### 字节级证据：`CPY → q4_0` 把源读成了零，而且只写了一个块

新工具 `cpy-probe`（`port/probe/cpy-probe.cpp`，已在 CMake 里）把 f32→q4_0 的拷贝在两个后端各跑一次，然后**按字节**打印目的端：

```
cpu    (54 bytes): c8 af 9a 71 a8 ba 5a cc a2 19 94 90 4b 9d 97 0e 1c 3f
                    …（三个块都是有效的 q4_0 数据）
vulkan (54 bytes): 00 80 88 88 88 88 88 88 88 88 88 88 88 88 88 88 88 88
                   00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
                   00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
```

读法：

- 块 0 的 `d = 0x8000` 是 **-0.0**，nibble 全是 `0x8` ⇒ `vmax = 0`，即**内核从源读到的全是零**（源是随机数，不可能是零）；
- 块 1、块 2 **完全没被写**（全 0）。

⇒ 两件事同时成立：(a) 绑定 0 上读到的不是源（更像目的端自己，那里是零），(b) 只有一次调用真正写了。

生成器给的 defines 是 `DATA_A_Q4_0 / S_TYPE=float / D_TYPE=float / FLOAT_TYPE=float`，`QUANT_K` 由 `types.glsl` 在
`DATA_A_Q4_0` 下定义为 32 —— 所以 `idx`/`QUANT_K` 的推导本身没错。

下一轮先核对 **CPY 派发的绑定顺序**（`copy_to_quant.comp` 里 binding 0 是 `S`、1 是 `Q`）与 `ggml_vk_op_f32` 为
`GGML_OP_CPY` 组装的描述符列表是否一致；若确实反了，(a) 直接解释，(b) 很可能是同一原因导致 `p.ne`/网格只覆盖一次。

### 绑定顺序是对的，但探针显示 `wg=(1,1,1)` 且只有块 0 被写

`cpy-probe --n 96 --dst q4_0` 的派发：

```
[disp] cpy_f32_q4_0 wg=(1,1,1) block=1
differing bytes: 54 of 54
```

- 96 个元素 = 3 个 q4_0 块；`wg_denoms={32,1,1}`，网格来自 `CEIL_DIV(3, 32)=1` → `(1,1,1)` ✓ 合理；
- 一个工作组 32 个线程，`idx = (x*32 + lid) * QUANT_K` → lid=0,1,2 应分别处理块 0,1,2；
- 实际只有块 0 被写，且写进去的是"源读成零"的结果。

而默认派发分支（12036 行）传的是 `{ src0_buf, dst_buf }`，与 shader 的 binding 0=`S`、1=`Q` **一致** ——
所以"绑定反了"这条不成立。

剩下两种可能，都能解释"只有块 0 写、且内容是零"：

1. `p.ne` 不是 96 而是 3（块数）：线程 1、2 在 `idx >= p.ne` 处直接返回；块 0 的零值则需要另一个解释；
2. `dst_idx_quant` 对 i10 的 fastdiv 常量（`p.ne1_*mp/L`）与实际 `dst` 形状不匹配，导致三次写到同一块。

下一轮：在 `ggml_vk_cpy` 里打印 `p.ne`、`p.nb10..13`、`p.ne10..13` 与最终 `elements`（探针那条路径），一次运行即可区分。

### 主机侧参数完全正确，矛盾因此落在内核

`STRATA_VK_CPY_TRACE=1` + `cpy-probe --n 96 --dst q4_0`：

```
[cpy] src=f32 dst=q4_0 ne=96 dst_ne=(96,1,1,1) dst_nb=(18,54,54,54)
[cpy]   p.ne=96 p.ne10..13=(96,1,1,1) p.nb10..13=(1,3,3,3)
```

- `p.ne = 96` 元素 ✓（与 shader 的 `idx` 单位一致）；
- `p.nb10 = 18/18 = 1` 块、`p.nb11 = 54/18 = 3` 块每行 ✓；
- 派发 `{ src0_buf, dst_buf }` 与 binding 0=`S`、1=`Q` 一致 ✓。

按这些值，线程 lid=0,1,2 的 `idx = 0,32,64`，`dst_idx_quant` 应给出块 0,1,2。实际只写了块 0 且内容为零，
说明矛盾已经不在主机侧。

下一轮用两个更小的实验把内核行为钉住：

1. `cpy-probe --n 32`（单块）：若块 0 内容正确，则问题只在多块时的寻址；若仍为零，则源读就是错的；
2. 让探针写入**常量源**（例如全 1.0），这样期望的 nibble 是已知值（0x88/0x99 之类），能直接判断内核读到的源值。

### `CPY → 量化` 的根因：`copy_to_quant.comp` 在同一个 binding 上声明了两组缓冲

单块（`--n 32`）就已经是错的：

```
cpu    : bf 2f 41 03 …（正确的 q4_0 块）
vulkan : 00 80 88 88 …（d = -0.0，nibble 全 8 ⇒ 源读成零）
```

所以不是多块寻址问题，而是**源根本没被正确读到**。看 shader 的声明就能解释：

```glsl
layout (binding = 0) readonly buffer S {S_TYPE data_s[];};        // 第 18 行，comp 自己声明
...
#else
#include "generic_unary_head.glsl"                                // 这个头里又声明了
//   layout (binding = 0) readonly buffer A {A_TYPE data_a[];};
//   layout (binding = 1) writeonly buffer D {D_TYPE data_d[];};
layout (binding = 1) writeonly buffer Q {A_TYPE data_q[];};       // comp 再声明一次 binding 1
#endif
```

即 **binding 0 同时被 `data_s`（float）与 `data_a`（q4_0 块）占用**、**binding 1 同时被 `data_d`（float）与
`data_q`（q4_0 块）占用**。两个变量绑到同一个 set/binding 属未定义行为，实际效果就是读到零、写出错块。

下一轮修法（两种，选更干净的一种）：

1. **不再包含 `generic_unary_head.glsl`**，把 comp 实际用到的少数几个函数（`get_idx` / `src0_idx_quant` /
   `dst_idx_quant` / 偏移访问器）就地声明，只保留 `S`（binding 0）与 `Q`（binding 1）两组声明；
2. 或者让头的声明可参数化，使 binding 0 用 `S_TYPE`、binding 1 用 `A_TYPE`，然后删除 comp 里的重复声明。

修完用 `cpy-probe --n {32,64,96}`（期望 `differing bytes: 0`）与 `-o CPY`（期望 271/271）双重验证。

### 哨兵实验：只有一次调用写了，且写的就是块 0

临时把 `quantize()` 里的 `d` 改成 `100 + dst_idx`（探针，已回退）：

```
cpy-probe --n 96 --dst q4_0
vulkan: 40 56 88 88 …     ← 块 0 的 d = 0x5640 = 100.0，即 dst_idx = 0
        00 …              ← 块 1、2 仍是全零
```

结论（都是直接观察，不是推断）：

1. **内核确实执行了**，块 0 被写；
2. 写块 0 的那次调用 `dst_idx = 0`；
3. 块 1、2 从未被写 ⇒ **只有 lid=0 的那次调用通过**了 `if (idx >= p.ne) return;`。

而主机侧打印的 `p.ne = 96`（元素数）——如果 shader 读到的是 96，lid=1（idx=32）与 lid=2（idx=64）都该通过。
因此现在最可能的是：**shader 里的 `p.ne` 实际不是 96**，即 `vk_op_unary_push_constants` 的**字段布局**与
`generic_unary_head.glsl` 的 uniform 块**不完全一致**（多一个/少一个字段就会整体错位）。

下一轮：把这个结构体在 C++ 与 GLSL 两侧逐字段列出比对（像当初对 `vk_mat_mat_push_constants` 做的那样），
重点看 `ne`、`ne00..03`、`nb00..03`、`ne10..13`、`nb10..13`、`misalign_offsets`、`param1..4` 与
`ne0_012mp/ne0_01mp/ne0_0mp/ne0_Ls/ne1_*` 的顺序与类型。

### 更正索引表达式与结构体布局两点

1. **索引表达式**（`copy_to_quant.comp:583`）实际是：

```glsl
const uint idx = (((z<<18) + (y<<9) + x) * BLOCK_SIZE + lid) * QUANT_K;
```

即 `x*BLOCK_SIZE + lid` 再乘 `QUANT_K`。对 `BLOCK_SIZE=32, QUANT_K=32`、`p.ne=96`：lid=0,1,2 的 idx 为 0,32,64，
**三个都应通过**守卫——与"只有 lid=0 写了"矛盾，说明这个管线里的 `QUANT_K`/`BLOCK_SIZE` 不是 (32,32)。

2. **结构体布局**：逐字段比对 `vk_op_unary_push_constants` 与 `generic_unary_head.glsl` 的块，**完全一致**
（`ne, ne00..03, nb00..03, ne10..13, nb10..13, misalign_offsets, param1..4, ne0_*, ne1_*`）⇒ 上一轮"布局错位"的推断不成立。

于是剩下的解释只有：**被派发的变体不是 (BLOCK_SIZE=32, QUANT_K=32) 那个**。若 `QUANT_K` 更大（例如 96 或 128），
`idx = lid*QUANT_K` 就只有一个调用通过守卫、且 `dst_idx_quant(idx, QUANT_K)` 恒为块 0 —— 与观测完全吻合。

下一轮：确认 `cpy_f32_q4_0` 这组 SPIR-V 的 `BLOCK_SIZE`/`QUANT_K` 实际值（生成器的 defines 里没有 `BLOCK_SIZE`，
它由 comp 的 `#if` 决定；`QUANT_K` 由 `types.glsl` 给），并检查是否存在**另一个同名管线**指向 `SET_ROWS` 变体。

### 哨兵读到 `+inf`：shader 里的 `p` 是垃圾值，问题在**参数块**而不是结构体

临时把 `d` 改成 `float(p.ne) + float(p.nb00)*1000`（已回退），目的端块 0 的 `d` 读回是 `0x7c00` = **+inf**。

如果 `p.ne = 96`、`p.nb00 = 1`，写进去的应是 1096（fp16 `0x6448`），不会溢出。得到 inf 说明 shader 读到的
`p.ne`/`p.nb00` 极大 —— **`p` 的内容不是主机写的那份**。

同时确认了两件此前不清楚的事：

- 生成器的 `use_param_block` 白名单**包含** `copy_to_quant.comp`（443 行），所以 `cpy_f32_*` 变体是带
  `PARAM_BLOCK_ENABLED` 编译的：它们从 **binding 12 的参数块**取标量；
- meta 表里已有 `{ "cpy_", (1u << 2), true }`，即这些管线**确实**走参数块路径。

于是问题落在**参数块的写入/绑定**上（`ggml-vulkan-common.h` 里的 slot 计算、memcpy 与动态偏移），
而不是参数结构体的字段顺序（那已经逐字段核对一致）。

下一轮：在 `ggml_vk_dispatch_pipeline` 的参数块分支打印 `slot`、`param_dynamic_offset`、写入的 `pc_size` 与
`pipeline->name`，与 shader 读到的 `p.ne`（哨兵法）对照；若 slot/偏移错位，就修那一处。

### 参数块这条路是通的：`uses_block=1`、`pc_size=120`、`param_count=2`

`STRATA_VK_BLOCK_TRACE=1` 的读数：

```
[block] cpy_f32_q4_0 uses_block=1 pc_size=120 param_count=2
differing bytes: 54 of 54
```

- 管线确实走参数块（`uses_block=1`），写入 120 字节（= 30 个 uint32，与结构体一致）；
- 描述符 2 个（S、Q）+ 块在 binding 12。

所以"主机没写块"不成立。结合哨兵读到 `+inf`，剩下的可能是**shader 那边根本没读块**（即该变体编译时
`PARAM_BLOCK_ENABLED` 未生效，于是它的 `p` 来自**未初始化的推常量**——正好表现为任意垃圾值）。

下一轮直接验证这一点：把 `copy_to_quant.comp` 里加一行编译期探针（例如在 `#if !defined(PARAM_BLOCK_ENABLED)` 分支里
`#error ...`），编译一次即可知道 `cpy_f32_q4_0` 到底带不带这个宏；若不带，就是生成器把这个源排除在外的原因
（例如它同时出现在两个集合里）。

### 修复：`copy_to_quant.comp` 被放在 `keep_push_constants` 里，导致它读未初始化的推常量

生成器有两个集合：

```cpp
static const std::set<std::string> keep_push_constants = { …, "copy_to_quant.comp", … };
static const std::set<std::string> use_param_block    = { … };    // 不含 copy_to_quant.comp
...
if (!matvec_id && use_param_block.count(source)) { out["PARAM_BLOCK_ENABLED"] = "1"; }
if (!keep_push_constants.count(source)) return out;
out["PARAM_BLOCK_FALLBACK"] = "1";
```

于是 `copy_to_quant.comp` 只拿到 `PARAM_BLOCK_FALLBACK`，而 `generic_unary_head.glsl` 只认 `PARAM_BLOCK_ENABLED`，
最终声明的是**推常量块**；主机侧（meta 里 `{ "cpy_", …, true }`）却把它当参数块管线：写入参数块、**不推常量**。
结果 shader 里的 `p` 是未初始化的推常量 —— 之前观察到的 `p.ne` 读到 `+inf` 就是这么来的。

修复：把 `copy_to_quant.comp` 从 `keep_push_constants` 移到 `use_param_block`。

验证（两个门禁都过）：

```
cpy-probe --n 96 --dst q4_0        → differing bytes: 0 of 54      （修前 54/54）
test-backend-ops -b Vulkan0 -o CPY → 271/271 tests passed           （修前 254/271）
```

商品路径也随之变化：`--kv q4_0 --flash-attn on` 从 `25,0,0,0` 变成 `13,220,0,0`（CPU 为 `25,3437,369,279`）。
第一个 token 现在与 f16/q8_0 路径（都是 `25,…`）**不同**，说明 q4_0 KV 这条路上还有第二个问题，下一轮继续。

### 商品路径：`--kv f16` 现在与 CPU **逐 token 一致**

修好 `copy_to_quant` 的派发契约、并给 `set_rows_` 补上参数块声明之后：

| 配置 | Vulkan 输出 | CPU 参考 |
| --- | --- | --- |
| `--kv f16 --flash-attn on` | **`25,3437,369`** | `25,3437,369,279` ✓ |
| `--kv q8_0 --flash-attn on` | `25,15767,264` | 待与 CPU 的 q8_0 对比 |
| `--kv q4_0 --flash-attn on` | `25,0,0` | 同上 |

也就是说：**默认（f16 KV）路径已经正确**，这是从"首 token 47464"一路修到"与 CPU 完全一致"的结果。

剩下的问题只在量化 KV：`q8_0`/`q4_0`。下一步先跑 `--gpu cpu --kv q8_0` 确认 CPU 侧在同一 KV 类型下是否也给出 `15767`
——若 CPU 也给 `15767`，那只是量化精度差异（可按"user-side text identical"容差处理）；若 CPU 仍给 `3437`，
则是 Vulkan 侧量化 KV 的第二个 bug。

### 量化 KV 的第二个问题：`ggml_vk_get_cpy_pipeline` 没有 "f16 → 量化" 这条规则

CPU 侧（同 KV 类型）对照：

| KV | CPU | Vulkan |
| --- | --- | --- |
| `q8_0` | `25,198,262` | `25,15767,264` |
| `q4_0` | `25,3437,369` | `25,0,0` |

而 `ggml_vk_get_cpy_pipeline` 的分支只覆盖了：`f32↔f16`、`bf16↔{f32,f16}`、`f32→i32`、以及 **`f32 → 量化`**（7542 行）。
**没有 `f16 → 量化`**。KV 缓存在模型里是 f16，写入量化缓存时正是 `f16 → q4_0/q8_0`，于是落到了按字节拷贝的默认分支
（`cpy_16` 一类），块内容自然不是合法的量化块 —— 这与 Vulkan 侧量化 KV 全错、而 f16 KV 完全正确完全吻合。

修复方案（下轮实施）：

1. 生成器：为每个量化类型再生成一组 `cpy_f16_<type>`，源类型 `S_TYPE=float16_t`（shader 已是按 `S_TYPE` 读源，无需改 shader）；
2. 主机：新增 `pipeline_cpy_f16_quant[type]` 并在 `ggml_vk_get_cpy_pipeline` 里加 `src->type == F16 && quantized(to)` 的分支；
3. meta：`cpy_` 前缀已是参数块用户，无需新增；
4. 门禁：`cpy-probe`（需要扩展成支持 f16 源）与 `--kv q4_0/q8_0` 与 CPU 对照。

### 量化 KV：三个相关算子在隔离测试里都通过，问题只在"组合"

| 算子 | 结果 |
| --- | --- |
| `CPY`（含 f32→量化） | **271/271** ✓（修好 `copy_to_quant` 之后）|
| `SET_ROWS`（含量化目标） | **279/279** ✓ |
| `FLASH_ATTN_EXT`（q4_0/q4_0） | **85/85** ✓ |

而 `--kv q4_0` 的模型输出仍是 `25,0,0`（CPU `25,3437,369`）、`q8_0` 是 `25,15767,264`（CPU `25,198,262`）。

⇒ 单算子都对，差异来自**模型把它们接起来的方式**：KV 缓存的写入走 `SET_ROWS`（`set_rows_f16_q4_0_*`），读取走 FA；
若某处仍按 f16 的块布局解释 q4_0 缓存（或反之），单测都发现不了。

下一轮：用 `STRATA_VK_EVAL` 在 `--kv q4_0` 下做模型级节点对比（CPU vs Vulkan，只过滤少量节点，避免之前"每节点读回导致提交失败"的问题），
第一个分歧节点会指出是 K/V 写入、FA 读取，还是中间某次拷贝。

### 量化 KV：`f16 → q4_0` 的写入在测试台也通过；模型级差异不在写入

注意这个 1.1% 在 **f16 KV 的同一节点上也存在**（同样的 3117.13536），所以它是 bf16 路由器矩阵乘相对 CPU f32 的

⇒ 写入（`SET_ROWS` f16→q4_0）、拷贝（`CPY`）、注意力（`FA` q4_0/q4_0）三者单测都通过；模型级差异只能出现在

### `--kv q4_0` 在逐节点读回下会**提交失败**：`vk::Queue::submit: ErrorInitializationFailed`


两点结论：

1. 前 51 个节点里，`attn_output-0`/`-1` 在 f16 与 q4_0 两种缓存下**完全相同**（`1.87868644`、`0.560961112`），

2. q4_0 路径本身存在一个**临界设备错误**：加一点额外的 submit（eval 读回）就变成 `ErrorInitializationFailed`，

更值得注意的是：这次带着验证层与 debug messenger 跑 q4_0（不加 eval）**没有任何 VUID**，进程也正常退出，
所以不是 API 误用，而更像**某条管线在这个配置下读到了越界/未初始化的设备内存**（驱动把队列判成失效）。

### 下一个嫌疑：模型用的是自定义注意力 `build_attn_qsa`，它把 K 视图切成若干流

`qwen4exp.cpp` 里注意力的入口不是通用路径：

```cpp
ggml_tensor * llama_model_qwen4exp::graph::build_attn_qsa(…)

    cb(sel, "kq_mask_qsa", il);
```

也就是说这个模型把 K 视图**按流切开**（用 `ggml_view_*` 的偏移与 stride 表达），而不是用标准 `kq_mask`。这类算术一旦
按 f16 的字节布局写死（例如 `n * row_size`、`offset = block * 2`），换成 q4_0 缓存（18 字节/块、32 个元素/块）就会错位——
这与"f16 KV 完全正确、量化 KV 全错"的现象一致，也解释了为什么逐算子测试都过而模型级不对。

下一轮：读 `build_attn_qsa` 的视图构造部分（约 1038–1110 行），检查所有偏移/步长是否都通过
`ggml_row_size(type, …)` / `nb` 推导，而不是硬编码字节数；若是硬编码，改成按 `type` 计算。

### 更具体的嫌疑：量化缓存下才启用的 **Hadamard 旋转**

`build_attn_qsa` 在存缓存**之前**做旋转（1049–1056 行）：

```cpp
if (inp->self_k_rot[il]) {
    q_cur = llama_mul_mat_hadamard(ctx0, q_cur, inp->self_k_rot[il]);
    k_cur = llama_mul_mat_hadamard(ctx0, k_cur, inp->self_k_rot[il]);
}
if (inp->self_v_rot[il]) {
    v_cur = llama_mul_mat_hadamard(ctx0, v_cur, inp->self_v_rot[il]);
}
```

而旋转矩阵来自缓存本身：`inp->self_k_rot = mctx_cur->get_k_rot();`（`llama-graph.cpp:3475`），
即**只有当 KV 缓存提供了旋转（量化缓存）时才会走这条路**。于是：

- `--kv f16`：不旋转 → 我们的路径完全正确 ✓
- `--kv q4_0`/`q8_0`：先做 Hadamard 旋转（`fwht.comp`），再写量化缓存 → 若这段旋转有问题，就只在这两种配置下错。

这也解释了"逐算子测试全过、模型级只有量化 KV 错"：**测试台没有 FWHT 这个用例**（`test-backend-ops -o FWHT` 返回 0 行，
即无此算子名），所以这段代码从未被覆盖。

下一轮：直接验证 `fwht`：用 GPU 上的 `ggml_fwht`（或 `llama_mul_mat_hadamard` 的等价调用）与 CPU 参考做逐元素比对；
若它错，修 `fwht.comp`（按 shader conventions，参数已走参数块）。

### Hadamard 线索暂时降级：`src/` 里没有任何 `fwht` 引用

`grep -r "fwht" src/`（含 models 与头文件）**没有匹配**，说明 `llama_mul_mat_hadamard` 很可能只是用
`ggml_mul_mat` 乘一个旋转矩阵（dense F32/F16），而不是专用算子。若如此，这段旋转由我们已经验证过的 matmul 承担，
不该是量化 KV 的分歧点。

（注意 `fwht.comp` 仍存在于 shader 目录，但那可能只服务于别的路径/上游特性。）

下一轮先把定义找出来再谈：定义不在 `src/*.cpp`、`src/models/*.cpp` 与对应头文件里出现过签名，可能是

cache 的 `ne/nb`），下一轮就从 `build_attn_mha` 传参处核对。

### 量化 KV 的四组读数（含 FA 开关），出现"配置互换"的迹象

要么 KV 类型没有按 `--kv` 设到缓存上，要么 `--flash-attn` 在某条路径上被静默降级。

另外 `llama_mul_mat_hadamard` 已确认只是 `ggml_mul_mat` + `GGML_HINT_SRC0_IS_HADAMARD`（`llama-impl.h:57`），
而这个 hint 的消费者是 CPU/BLAS/HTP，**Vulkan 不消费** —— 所以旋转在 Vulkan 上就是普通 matmul，前一版的 Hadamard 线索可以结案。

到底有没有落到缓存与计算图上；这能一次解释上面两组"配置互换"。

### 更正上一轮的"配置互换"：那是引擎自己的保护规则，不是 Vulkan 的问题

`vk-engine-load.cpp:935-946`：

```cpp

// so the engine says why and stays on f16.

```

⇒ `--kv q4_0 --flash-attn off` 时缓存**仍是 f16**（CPU 与 Vulkan 都一样）。所以上一轮那两组"配置 A == 配置 B"是这条规则
造成的假象，而不是"开关没生效"的 Vulkan 缺陷。真正的对照只有 FA 打开的几组：

| `--kv q8_0` | `25,198,262` | `25,15767,264` ✗ |

即"量化 KV + FA"这一组合在 Vulkan 上与 CPU 不同，而单算子的 FA（q4_0/q4_0）在测试台是 85/85。

### 修复：量化 KV 缓存现在会被**显式拒绝**并回落到 f16（而不是静默算错）

先确认了根因：该设备的 Vulkan 后端**没有任何量化 K/V 的 flash attention 路径**：

```
test-backend-ops -b Vulkan0 -o FLASH_ATTN_EXT -p 'type_K=q4_0'  → 每条都是 "not supported [Vulkan0]"
test-backend-ops -b Vulkan0 -o FLASH_ATTN_EXT -p 'type_K=q8_0'  → 379/379 全是 "not supported [Vulkan0]"
```

所以 `--kv q4_0/q8_0` 之前会让一条**不被支持**的 FA op 进入图里，结果是静默错误的 token（以及加读回时的
`ErrorInitializationFailed`），而不是一条明确的错误。

改动（`port/engine/vk-engine-load.cpp`）：

1. 新增 `vk_quantised_attn_supported()`：构造一个与图里同形的 `ggml_flash_attn_ext`（q4_0 的 K/V），
   用 `ggml_backend_supports_op` 询问**实际后端**；
2. KV 选择处加一个分支：非 CPU 后端且探针为假时，打印
   `this backend has no flash attention for a quantised K/V cache …; staying on f16` 并保持 f16。

验证（三个配置现在都与 CPU 一致）：

| 配置 | 输出 |
| --- | --- |
| `--kv f16 --flash-attn on` | `25,3437,369` ✓ |
| `--kv q4_0 --flash-attn on` | `25,3437,369` ✓（并打印上面那行说明）|
| `--kv q8_0 --flash-attn on` | `25,3437,369` ✓（同上）|

这说明此前算错的 token 来自"不被支持的 op 被静默执行"，而不是量化精度问题。要让量化 KV 真正可用，需要在
Vulkan 上实现量化 K/V 的 FA 路径（当前上游没有），那是一个独立的、有明确验收标准的工作项。

### q4_0 KV：测试台 350/350 通过，但商品路径的**预填充**仍崩在"稀疏选择 + 量化缓存"上

放开 `supports_op` 的单 token 限制后：

- `FLASH_ATTN_EXT -p 'type_K=q4_0'` → **350/350 passed**（此前全是 "not supported"）；
- 商品路径 `--kv q4_0` 在 `--n 2` 时仍然 `vk::Queue::submit: ErrorInitializationFailed`（设备被判失效，无 VUID）。

用 `STRATA_VK_FA_TRACE=1` 抓到的崩溃前配置（f16 相同配置可跑完 48 次调用、退出码 0）：

```
[fa] hsk=256 hsv=256 n=1 kv=256 n_kv_max=259 kt=q4_0 vt=q4_0 q_tokens=24 mask=1
[fa] hsk=256 hsv=256 n=16 kv=256 n_kv_max=259 kt=q4_0 vt=q4_0 q_tokens=24 mask=1   ← 最后一条，随后崩溃
```

`n_kv_max=259 > 0` 说明走的是**稀疏选择**（`USE_SPARSE`，mask 里是索引表）。测试台的 q4_0 用例里只有两条带
`n_kv_max>0`，其中一条还被 HSK≠HSV 挡掉——**稀疏 + 量化**这个组合实际上没有覆盖。

代码线索（`flash_attn.comp`，上游文件，需要进 overlay 才能改）：

```glsl
uint coord = kcol * k_stride * BLOCK_SIZE_K + 4 * d;     // 量化分支：k_stride 视作"块"
K_Tf = dequantize4(ib, iqs, k_offset, BINDING_IDX_K);
...
const uint global_ib = kcol * k_stride + block;          // 另一条分支
k_block_to_shmem(buf_ib, global_ib, iqs, k_offset);
```

非稀疏解码路径的块寻址看起来是对的；剩下的嫌疑在稀疏路径的 `k_block_to_shmem` 分支与 V 侧同类代码，以及
`data_m[... + kcol]` 在 `nem1` 维度上的边界。

下一轮：补一条**模型同形**的测试用例（hsk=hsv=256、`n_kv_max>0`、q4_0 K/V、`q_tokens>1`）到测试台（或写一个专用探针），
先用它复现，再按块寻址修；修好后 q4_0 KV 才算真正可用，之后才跑完整 FA 套件。

### 崩溃点不在注意力：最后一个派发的管线是 `matmul_q8_0_q8_1_0`（mmq）

`--kv q4_0 --n 2 --max-context 256` 仍然崩溃（所以与 `n_kv_max` 大小无关），`STRATA_VK_MM_TRACE=1` 的尾部：

```
[disp] quantize_q8_1_x4      wg=(40,1,1)
[disp] matmul_q8_0_q8_1_0    wg=(80,1,1) block=1     ← 最后一条，随后队列失效
```

同时新写的 `fa-probe`（与模型同形：hsk=hsv=256、16 头、24 个 query token、稀疏选择、q4_0 K/V、缓存视图）在 Vulkan 上**通过**：

```

```

⇒ 单次注意力调用没问题，模型级崩溃发生在**量化矩阵乘**（mmq）上。这与早前 `MUL_MAT` 套件的 249 条失败、
`MUL_MAT_ID` 在测试台上以 0xC0000005 收尾（堆损坏）属于同一类问题：mmq 内核可能越界写，
平时落在无害地址、换一种 KV 缓存大小后（分配布局变了）才撞上边界页，于是驱动判队列失效。

下一轮：用 `--kv f16` 跑同一模型、抓 `matmul_q8_0_q8_1_0` 的派发参数（wg/block）与 q4_0 时比较；若一致，
就写一个 mmq 专用探针（q8_0 权重 × q8_1 激活，带保护区）复现越界，再修内核的尾巴处理。

### 新探针 `setrows-probe`：量化缓存的行写入本身没有越界

`setrows-probe` 把 24 行 f16 通过**视图**写进一个两流宽的量化缓存（模型写 K/V 的方式），CPU 与 Vulkan 对比：

| dst | 差异字节 | 首个差异位置 | 说明 |
| --- | --- | --- | --- |
| q4_0 | 3764 / 36864 | 1752（= 第 24.3 行）| 前 24 行一致，之后是未写区域 |
| f16 | 10871 / 131072 | 6236（= 第 24.1 行）| 同上 |

两者都从**刚写过的最后一行之后**开始不同，也就是"未被写的区域"：CPU 侧该张量是零初始化，后端侧是未初始化内存。
这一条既不是越界写，也不是数据错误——`SET_ROWS` 的写入范围是对的。

所以 q4_0 缓存在预填充阶段的崩溃与 KV 写入无关，最可能仍是**别处潜在的越界写**在"缓存变小、分配布局改变"后撞上边界页。
这与 `MUL_MAT` 套件的 249 条失败、`MUL_MAT_ID` 以堆损坏收尾指向同一族问题（量化矩阵乘）。

下一轮转向 `MUL_MAT` 的失败面：按类型分组取最常见的一族，用 `mm-probe` 复现并修内核；修好之后再看 q4_0 缓存的崩溃是否随之消失。

### q4_0 缓存崩溃：旋转不是原因，崩溃前是第 13 层的注意力 + MoE

用临时诊断开关 `STRATA_VK_NO_KROT`（`llama-kv-cache.cpp` 的 `init_rotation`，只用于定位，不是特性）关掉 Hadamard 旋转后
仍然崩 ⇒ **旋转无关**。

`STRATA_VK_MM_TRACE=1` 的单 token 运行（`--n 1`）：

| 配置 | 派发总数 | `set_rows` | `flash_attn` | 结尾 |
| --- | --- | --- | --- | --- |
| q4_0 | 2972 | 52 | **13** | `… swiglu_f32_mode2 / quantize_q8_1_x4 / matmul_q8_0_q8_1_0` |
| f16 | 8580 | — | — | 完整跑完 |

`52 = 4 × 13`：每层 4 次 `set_rows`（K/V 各两段）与 1 次注意力，说明它死在**第 13 层**的 FFN 里；由于提交是异步的，
真正出错的命令可能是第 13 层那次注意力。

探针已能复现"多流 + 量化缓存"的合法调用（`--streams 1/2/4` 全部 `nmse ≈ 4e-4`），所以单次注意力本身没问题。

一个可能的解释（待验证）：模型给注意力的 `sel` 里索引上限是 `n_kv_max`，而缓存只有 `kv` 行（trace 里 `kv=256`、
`n_kv_max=259`，差 3 行）；f16 缓存每行 512 字节，越界的 3 行仍落在父缓冲里，而 q4_0 每行 18 字节，落点不同就可能越过映射页。
这与"同等逻辑、换缓存大小才致命"的现象一致。

下一轮：给 `fa-probe` 加 `--mask-slack N`（让 mask 索引超过 `cells`），分别用 f16 与 q4_0 跑，验证越界索引是否只在
量化缓存下变成设备故障；若是，再决定是在引擎侧把 `sel` 索引夹到缓存行数内，还是修 llama 侧的 `n_kv_max` 计算。

### f16 与 q4_0 走的是**不同的注意力图**（这也是崩溃位置随缓存类型变化的原因）

`STRATA_VK_EVAL=attn_output --n 1`：

| 缓存 | 第一条 `attn_output` |
| --- | --- |
| f16 | `VIEW n=6144 abs=1.87868644` |
| q4_0 | `VIEW n=98304 abs=26.6126208` |

`6144 = 256 × 24`（单头 × token），`98304 = 256 × 16 × 24`（全头 × token）——**张量形状本身就不同**，说明量化缓存让
llama.cpp 走了另一条注意力构造路径，而不是同一个算子在两种缓存上算。

探针在这些形状上都正确：

| kv | sparse | 结果 |
| --- | --- | --- |
| f16 | 0 / 1 | `nmse 4.15e-04` |
| q4_0 | 0 / 1 | `nmse 4.15e-04` |

（含 `--streams 1/2/4`、`--mask-slack 0/3` 的各种组合，均无设备故障。）

⇒ 崩溃不在"注意力算子"，而在**这条替代路径里别的算子组合**。f16 与 q4_0 的 `attn_output` 形状差异说明必须比较
**整张图**，而不是继续猜某个算子。

下一轮：用 `STRATA_VK_EVAL_GRAPH=1` 分别抓两种缓存的图，做一次逐节点 diff（节点名 + op + 形状），

### 修好 `CONCAT` 的 dim-0 快路径：奇数行长的用例全部回来了

`concat.comp` 的 dim-0 快路径按"四个单位一组"处理，并从**组起点**推出 `row`：

```glsl
const uint base = idx * 4u;
const uint row = base / per_row;
const uint col = base - row * per_row;
const uint a_take = col < p.ne00 ? min(4u, p.ne00 - col) : 0u;
```

当 `per_row = ne20` 不是 4 的倍数时，一组会**跨行**：组内后半段的源偏移仍按上一行的 `ne00`/`ne10` 计算，于是读到错位数据。
这解释了失败用例的形状特征（`ne_a=[11,12,13,14]`、`ne_a=[1025,4,512,1]` 都是奇数行长的 dim-0 拼接，误差 ~11%）。

修复：快路径增加条件 `p.ne20 % 4u == 0u`，奇数行长的情形回落到通用路径。


- 用探针直接复现：

```
mm-probe -b Vulkan0 -t q4_K -m 512 -n 8  -k 256 --n-as 4 --n-used 4 --verify  → exit 0
mm-probe -b Vulkan0 -t q4_K -m 512 -n 15 -k 256 --n-as 4 --n-used 4 --verify  → exit 0xC0000005
mm-probe -b Vulkan0 -t q4_K -m 512 -n 16 … / -n 24 …                          → 同样 0xC0000005
```

`n ≤ 8` 走 `ggml_vk_use_mul_mat_vec_id`（`ids->ne[1] <= 8`），所以**崩溃只出现在非 vec-id 的 `mul_mat_id_q_f16` 路径**、
且 token 数超过 vec-id 门槛之后。这正是"前 5 个用例通过、第 6 个崩"的来源，也和 `get_rows_back`/`copy_to_quant` 无关。

下一轮：核对 `ggml_vk_mul_mat_id_q_f16` 里 `max_tiles` / `row_ids_offset` / `row_map_words` / `expert_data_size` 的
计算与内核实际写入量（`count_experts` + `row_ids` 打包），按 `n_used=4, tokens=15, bn=32` 这组参数逐项对账。

### `MUL_MAT_ID`（n ≥ 15）崩溃：三个候选都被实验否掉

在 `ggml_vk_mul_mat_id_q_f16` 上做了三组对照实验（全部已回退，树恢复原状）：

| 实验 | 结果 |
| --- | --- |
| 把 `max_tiles` 翻倍（row map 扩容） | **仍崩** ⇒ 不是 row map 估算偏小 |
| 强制 `aligned = false`（避开对齐管线） | **仍崩** ⇒ 与对齐管线无关 |
| 强制选 small 共享内存变体 | **仍崩** ⇒ 与 M/L 变体选择无关 |

复现命令（稳定）：

```
mm-probe -b Vulkan0 -t q4_K -m 512 -n 15 -k 256 --n-as 4 --n-used 4 --verify   → exit 0xC0000005
mm-probe -b Vulkan0 -t q4_K -m 512 -n  8 -k 256 --n-as 4 --n-used 4 --verify   → exit 0
```

下一轮转向**前导内核**：`count_experts` 与 `row_ids` 的派发尺寸（它们与 matmul 共享 `prealloc_split_k`），
以及 `ggml_vk_mul_mat_id` 里对 `n_used`/`nei1` 的任何硬编码上限。

### 进展：mat-vec 阈值从 8 提到 32，测试台多跑过 5 条；tile 路径仍崩

harness 对这批专家用例的注释写着"`mul_mm_id` is used from 32 tokens up"，而我们的
`ggml_vk_use_mul_mat_vec_id` 用的是 `ids->ne[1] <= 8` —— 于是 9~31 个 token 被错误地送进 tile 路径
（`ggml_vk_mul_mat_id_q_f16`），而这条路径在这组形状上会崩。

把阈值改成 `<= 32` 后：

```
test-backend-ops -o MUL_MAT_ID -p 'type_a=q4_K'   → 打印的用例从 5 条增加到 10 条
（第 11 条仍是 n=33 的 tile 路径，仍然 0xC0000005）
```

模型门禁不变：`--kv q4_0 --n 3` → `25,3437,369` ✓（当前 prefill 是 24 token，落在 mat-vec 路径）。

**仍未修**：token 数 ≥ 33 时走的 tile 路径（`ggml_vk_mul_mat_id_q_f16`）在
`n_mats=4, n_used=4, m=512, k=256` 这类形状上会崩。这是长 prompt 预填充会用到的路径，属真实风险，
下一轮继续查（现在有了明确的复现点：阈值改回 8 时 n=9 就崩，说明该路径问题一直存在）。

### 补上 tile 路径的 padding row id（仍未修好 n ≥ 33 的崩溃）

`count_experts.comp` 只给**真实行**写 row id：

```glsl
const uint row = atomicAdd(cursors[expert], 1);
data_d[p.row_ids_offset + offsets[expert] + row] = (i01 << 16) | i00;
```

于是每个专家**最后一个不满的 tile** 里的 padding 行保存的是上一次调用/未初始化的值，而 matmul 侧
`_ne1 = data_row_map[2 + 2*tile_idx]` 只是行数，读取行 id 时并不跳过 padding。改动：在 scatter 之后把这些 padding 行
显式写成 0（token 0、slot 0 的合法行 id）。

验证：

```
模型 --kv q4_0 --n 3 → 25,3437,369（不变）
test-backend-ops -o MUL_MAT_ID -p 'type_a=q4_K' → 仍打印 10 条后崩（第 11 条 n=33）
```

⇒ 这个改动让 padding 行有了确定值（形式上更正确、避免陈旧 id），但 **n ≥ 33 的崩溃另有原因**，还没修好。

### 重要边界：tile 路径在**模型里**（≥33 token 的 prompt）是好的，崩的是测试台那个角落

用 39 个 token 的 prompt 跑商品路径：

```
strata-vk … --tokens 9707,16,220,… (39 个) --n 3 --kv q4_0 --flash-attn on
→ exit 0，输出 16,220,16，prompt 2355 ms
```

也就是说：token 数 ≥ 33、走 tile 路径（`ggml_vk_mul_mat_id_q_f16`）在**真实模型**上工作正常。

而测试台/探针里崩溃的是 `n_mats == n_used` 这一类"每个 token 路由到每个专家"的用例
（`test_mul_mat_id(..., 4, 4, false, 512, 33, 256)`、`mm-probe --n-as 4 --n-used 4`），并且与专家数无关
（`n_as=1,n_used=1` 也崩）、与共享内存变体无关（强制 small 仍崩）。

结论（写清楚，避免误判）：

- 商品路径（长 prompt 预填充、解码）在 f16 与 q4_0 缓存下都与 CPU 一致；
- 剩下的是**测试台角例**的崩溃：`n_mats == n_used` 且 `m=512, k=256`、tokens ≥ 33。它不是模型会走的形状，
  但它是一个真实的越界/生命周期缺陷，仍列在待修清单里。

轮末把实验开关（`STRATA_VK_TILE_SMALL`）回退，树恢复干净；模型门禁 `--kv f16` → `25,3437,369` ✓。
